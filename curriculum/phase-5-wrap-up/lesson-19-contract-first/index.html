Lesson 19: Contract First

Story

Ilona is building Fiona's screens and keeps knocking on your desk. "What does PUT want in the body? Is the fleece length called fleeceLength or fleeceLengthCm? What do I get back when the pen does not exist?" Every answer is in your code, but Ilona does not read Java, and your docs/requests.http file only shows what you tried.

Hasi shakes his head. "Stop answering by pointing at code. Write the agreement down first, as a file you both can read. Then the code has to follow the file, not the other way round. If you change the file, Ilona sees it. If the code drifts away from the file, the compiler tells you."

🚜 Barn Briefing: the contract is a file

OpenAPI is a standard format for describing an HTTP API in a file (YAML or JSON): which addresses exist, which methods each one answers, what goes in (parameters, body), what comes out for which status, and the shape of every request and response. It is written for programs first: a tool can read it and write the code that calls the API from TypeScript, or the code that answers it in Java.

There are two ways to get such a file. Code first: you write the controllers, and a library reads them and produces the file. The file is then only as good as what the library can see: it sees annotations and method signatures, but not what a method decides while it runs (that a method calls ResponseEntity.created, or that a handler somewhere else turns an exception into a 404). The file can be wrong, and nobody notices. Contract first: you (and the frontend developer) write the file, and the controller code is built from it. The file is the truth, and the code has to fit.

Many teams work contract first, because the frontend and the backend can start from the same file on the same day. That is what you do today, as a refactoring: your API already works and your tests are green. Afterwards the behaviour must be exactly the same, only the source of truth has moved.

What the file can and cannot do. A generator turns it into shapes: one Java interface per group of endpoints (with the addresses, methods and status codes on it) and one record per schema. It cannot write the behaviour. Whether your code really answers 404 where the file promises 404 is still a question for your tests.

🌱 Spring Sprout: mappings on an interface, and code that is generated at build time

You have written @GetMapping and @PostMapping on controller methods. Spring MVC also reads them from an interface that the controller implements. So a controller can be a class that implements an interface and has no mapping annotations of its own: the interface says where, the class says what happens. Interface methods are always public, so the methods you write for them are public too. Docs: Request Mapping.

The interfaces are written by a Maven plugin, the openapi-generator-maven-plugin. Maven builds in phases, and the plugin hooks into the phase generate-sources, before compiling. It reads your YAML file and writes Java files into target/generated-sources/openapi, which Maven compiles together with your own code. Because target is rebuilt at every build, you never edit these files and never commit them. Plugin docs: the spring generator. The plugin is not managed by the Boot parent: you write its version into the pom.xml (7.27.0).

Your Task

Move the source of truth of the farm API into a file, without changing what the API does.

  • src/main/resources/api/openapi.yaml describes every endpoint you have built: addresses, methods, bodies, statuses, errors.
  • The three controllers implement interfaces generated from that file. They carry no mapping annotations.
  • Your hand-written request and response records are gone; the generated records take their place.
  • No existing test changes and all of them stay green. They are your safety net for the whole lesson.
  • Then you change the contract first once: the answer for an alpaca gets a new member, readyToShear.

Learning Goals

  • Tell contract first from code first, and say who holds the truth in each
  • Read an OpenAPI file and the Java code generated from it
  • Add a Maven plugin that generates sources, and keep generated code out of version control
  • Refactor on green tests, one small slice at a time
  • Find out where a generated shape is looser or stricter than your hand-written code, with the help of your tests
  • Change an API by changing the contract first and letting the compiler lead

Getting Started

  1. Safe start. Run all tests: green. Commit anything open. Check that your .gitignore contains target/. From now on, if an existing test turns red, your code or contract is wrong, not the test.
  2. The plugin and a tiny contract. Add the plugin to the pom.xml (Hint 1 has the configuration; the options are explained in the comments there) and create src/main/resources/api/openapi.yaml with one endpoint: GET /farm and the schema FarmResponse (name, pens, alpacas). Group it with a tag Farm: the plugin makes one interface per tag. Run mvn generate-sources (or reload Maven in your IDE) and then read what appeared in target/generated-sources/openapi: the interface FarmApi and the record FarmResponse. Find the address and the method of /farm in the interface. Find the three components of the record. Write one sentence in docs/api-notes.md: what in the file became what in Java?
  3. Implement the interface (compile error, then green). Let FarmController implement FarmApi (package alpacas.web.api). The compiler stops you: the class "does not override abstract method getFarm()". Write that method (public, same signature as in the interface; it returns a ResponseEntity). Delete the mapping annotation on your old method and delete your hand-written FarmResponse record; use the generated one from alpacas.web.model instead. Run all tests. FarmControllerTest was not touched and is green: it speaks HTTP, so it does not care who wrote the controller's mapping. Commit.
  4. Shearing, the second slice. Add the tag Shearing, the path /pens/{penName}/alpacas/{alpacaName}/shear with POST, and its answers: 200 with an alpaca (the schema AlpacaResponse) and the errors 404 and 409. Put the two path variables into components/parameters and the errors into components/responses, so you can refer to them later with $ref instead of copying (Hint 2). The error answers use the media type application/problem+json and a schema Problem with status, title, detail, instance and errors (a map from field name to message): that is what ApiExceptionHandler really sends. Regenerate. Your hand-written AlpacaResponse has a method from(Alpaca), and a generated record cannot have one. Create a small package-private class WebMapping with static methods that do the mapping instead (Hint 2), and let ShearingController implement ShearingApi. Delete the old record. All tests green, commit.
  5. Pens, the big slice, in two cuts. Tag Pens: first the reads (GET /pens, GET /pens/{penName}/alpacas, GET /pens/{penName}/alpacas/{alpacaName}, GET /alpacas/ready-to-shear), regenerate, implement them in PenController, delete the records that are now generated (PenSummaryResponse), all tests green, commit. Then the writes: POST /pens (201, 400, 409), POST on the alpacas (201, 400, 404, 409), PUT (200, 400, 404), DELETE (204, 404). Read your own controller and your earlier tests to get the statuses right; the contract has to say what the code does. Write the three request schemas with the rules you gave them in Lesson 11.

    A note on the names: a schema called Alpaca would produce a generated record Alpaca that clashes with your domain class alpacas.Alpaca. That is why the schemas keep the names of your old records (AlpacaResponse, CreateAlpacaRequest, ...).

  6. Let the tests find the gaps. For the text rules ("not blank") write the natural thing for a file: minLength: 1. Regenerate, fix the compile errors, and run all tests. A test of Lesson 11 turns red: the one that sends several wrong fields at once and expects an error for each (it expects three and gets two). Open the generated CreatePenRequest (or CreateAlpacaRequest) and look at the annotation on name: @Size(min = 1). A string with only a space has length 1. Your old @NotBlank rejected it, the contract as you wrote it accepts it. The generated code is faithful to the contract, and the contract is looser than your code. Fix the contract, not the test: describe "at least one character that is not a space" with a pattern (Hint 3). Experiment first with pattern: '\S' (one non-space character) and run the suite: a dozen tests turn red, nearly every request is rejected. Open the generated annotation again (@Pattern(regexp = "\\S")) and think: in an OpenAPI file a pattern is "found somewhere in the text", but Bean Validation's @Pattern must match the whole text. Which pattern is right in both readings? Write both traps in docs/api-notes.md. Green, commit.
  7. Change the contract first. Fiona's screen should show a "Shear now" badge without calling another endpoint. So the answer for an alpaca gets a boolean member readyToShear. The order is the point: (a) test first: in PenControllerTest assert that $[0].readyToShear is false for the first alpaca of Ring. Red, because the member is missing. (b) Contract: add readyToShear (boolean) to AlpacaResponse in the YAML, in the list of required members. Put it last in properties: the order of the properties is the order of the components of the generated record. (c) Regenerate and read the compiler: the line in WebMapping that creates an AlpacaResponse no longer fits. The compiler has become your to-do list. Pass the missing value from the domain object (isReadyToShear()). Green, all tests, commit. (Your domain method still prints to the console; you know that wart from Lesson 01.)
  8. Read it as Ilona. Open openapi.yaml and imagine you never saw the Java code. Can you answer her three questions from the top of the lesson using only this file? What is missing for her? Write it down in docs/api-notes.md: it is input for Lesson 20.

Hints

Hint 1

The plugin, inside <build><plugins> (next to the Boot plugin). The options in configOptions decide what is generated:

<plugin>
    <groupId>org.openapitools</groupId>
    <artifactId>openapi-generator-maven-plugin</artifactId>
    <version>7.27.0</version>
    <executions>
        <execution>
            <goals><goal>generate</goal></goals>
            <configuration>
                <inputSpec>${project.basedir}/src/main/resources/api/openapi.yaml</inputSpec>
                <generatorName>spring</generatorName>
                <apiPackage>alpacas.web.api</apiPackage>
                <modelPackage>alpacas.web.model</modelPackage>
                <configOptions>
                    <useSpringBoot4>true</useSpringBoot4>           <!-- generate for Boot 4 -->
                    <useJackson3>true</useJackson3>                 <!-- Jackson 3 imports -->
                    <interfaceOnly>true</interfaceOnly>             <!-- interfaces and models, no controllers -->
                    <useTags>true</useTags>                         <!-- one interface per tag -->
                    <useRecords>true</useRecords>                   <!-- models are records -->
                    <skipDefaultInterface>true</skipDefaultInterface> <!-- methods are abstract -->
                    <openApiNullable>false</openApiNullable>
                    <annotationLibrary>none</annotationLibrary>     <!-- no Swagger annotations ... -->
                    <documentationProvider>none</documentationProvider> <!-- ... so no extra dependency -->
                </configOptions>
            </configuration>
        </execution>
    </executions>
</plugin>

The tiny contract and the controller:

openapi: 3.0.3
info:
  title: Fiona's Farm API
  version: "1.0"
tags:
  - name: Farm
paths:
  /farm:
    get:
      tags: [Farm]
      operationId: getFarm
      responses:
        "200":
          description: The farm in numbers.
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/FarmResponse"
components:
  schemas:
    FarmResponse:
      type: object
      required: [name, pens, alpacas]
      properties:
        name: {type: string}
        pens: {type: integer}
        alpacas: {type: integer}
@RestController
class FarmController implements FarmApi {
    ...
    @Override
    public ResponseEntity<FarmResponse> getFarm() {
        int totalAlpacas = pens.findAll().stream().mapToInt(Pen::totalAlpacas).sum();
        return ResponseEntity.ok(new FarmResponse(FARM_NAME, pens.findAll().size(), totalAlpacas));
    }
}

Imports: alpacas.web.api.FarmApi, alpacas.web.model.FarmResponse. The name of the method comes from operationId. Your IDE may need a Maven reload to see the generated sources.

Hint 2

Parameters and error answers that are defined once and used with $ref:

  /pens/{penName}/alpacas/{alpacaName}/shear:
    parameters:
      - $ref: "#/components/parameters/PenName"
      - $ref: "#/components/parameters/AlpacaName"
    post:
      tags: [Shearing]
      operationId: shearAlpaca
      responses:
        "200":
          description: The alpaca after shearing.
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/AlpacaResponse"
        "404":
          $ref: "#/components/responses/NotFound"
        "409":
          $ref: "#/components/responses/Conflict"
components:
  parameters:
    PenName:
      name: penName
      in: path
      required: true
      schema:
        type: string
    AlpacaName:
      name: alpacaName
      in: path
      required: true
      schema:
        type: string
  responses:
    NotFound:
      description: The pen or the alpaca does not exist.
      content:
        application/problem+json:
          schema:
            $ref: "#/components/schemas/Problem"
  schemas:
    Problem:
      type: object
      properties:
        status: {type: integer}
        title: {type: string}
        detail: {type: string}
        instance: {type: string}
        errors:
          type: object
          additionalProperties: {type: string}

(Conflict and BadRequest are built like NotFound, with their own description.) The mapping class and the controller that uses it:

final class WebMapping {

    private WebMapping() {
    }

    static AlpacaResponse toResponse(Alpaca alpaca) {
        return new AlpacaResponse(
                alpaca.getId(),
                alpaca.getName(),
                alpaca.getWeight(),
                alpaca.getFleeceLength(),
                alpaca.getFleeceColor().name());
    }
}
@RestController
class ShearingController implements ShearingApi {
    ...
    @Override
    public ResponseEntity<AlpacaResponse> shearAlpaca(String penName, String alpacaName) {
        return ResponseEntity.ok(WebMapping.toResponse(shearingService.shear(penName, alpacaName)));
    }
}

The same class gets toResponse(Pen) and the two toAlpaca methods (they replace from and toAlpaca of your old records). In PenController a method that used to have @PathVariable String penName now simply has String penName; the annotation sits on the interface.

The 201 answers with a Location header keep working: ResponseEntity.created(location).body(...) is still what you return.

Hint 3

The request schemas with the rules from Lesson 11. The pattern .*\S.* means "anything, one character that is not a space, anything": right in both readings (found anywhere, and matching the whole text).

    CreatePenRequest:
      type: object
      required: [name]
      properties:
        name: {type: string, pattern: '.*\S.*'}
    CreateAlpacaRequest:
      type: object
      required: [name, weight, fleeceLengthCm, fleeceColor]
      properties:
        name: {type: string, pattern: '.*\S.*'}
        weight: {type: number, format: double, exclusiveMinimum: true, minimum: 0}
        fleeceLengthCm: {type: integer, minimum: 0, maximum: 10}
        fleeceColor: {type: string, pattern: '.*\S.*'}

UpdateAlpacaRequest is the same without name (the name comes from the address). The response record with the new member, last in the list:

    AlpacaResponse:
      type: object
      required: [id, name, weight, fleeceLengthCm, fleeceColor, readyToShear]
      properties:
        id: {type: integer, format: int64}
        name: {type: string}
        weight: {type: number, format: double}
        fleeceLengthCm: {type: integer}
        fleeceColor: {type: string}
        readyToShear: {type: boolean}
static AlpacaResponse toResponse(Alpaca alpaca) {
    return new AlpacaResponse(
            alpaca.getId(),
            alpaca.getName(),
            alpaca.getWeight(),
            alpaca.getFleeceLength(),
            alpaca.getFleeceColor().name(),
            alpaca.isReadyToShear());
}

When You're Done

Reflect

  • Which of your tests protected you today, and which one would have noticed that the file says 404 while the code never answers 404? Does anything in the build check that the code does what the file promises?
  • The error answers in the file use a schema Problem with an errors member, but your handlers still return Spring's ProblemDetail. Who makes sure the two fit? What would happen if they drifted apart?
  • Ilona wants a new member in the answer. In a code-first project and in this one: who changes what, and in which order? Where does the compiler help, and where only a test?
  • Generated files live in target/ and are not committed. What does a new colleague need to do after cloning the repository, before the code compiles? What would change if they were committed?
  • The file calls the schema AlpacaResponse and not Alpaca. What does that say about the connection between names in the contract and names in the domain?
  • The contract describes the shape of an answer. Name something about your API that no OpenAPI file can say.
