Lesson 19: The Farm Explains Itself

Story

Ilona is building Fiona's screens and keeps knocking on your desk. "What does PUT want in the body? Is the fleece length called fleeceLength or fleeceLengthCm? What do I get back when the pen does not exist?" Every answer is in your code, but Ilona does not read Java, and your docs/requests.http file only shows what you tried.

Hasi has a better idea. "Write it down by hand and it is wrong by next week. Let the program describe itself. Then the description can never be older than the code. And Ilona can click on it and try the calls herself."

🚜 Barn Briefing: a description you can read, and a page that shows it

Two different things hide behind the word "Swagger", and it helps to keep them apart.

OpenAPI is a standard format for describing an HTTP API in a file (JSON or YAML): which addresses exist, which methods each one answers, what goes in (parameters, body), what comes out for which status, and the shape of every request and response. It is written for programs first. A tool can read it and write a client for a frontend, or check calls.

Swagger UI is a web page that reads such a description and shows it to humans: every endpoint as a box you can open, with a button Try it out that sends a real request to your running application.

The description can be generated from your code. That is its strength and its limit: the generator only knows what it can see. It sees your annotations and the types in your method signatures. It does not see what your method decides while it runs. Today you will find out exactly where that difference lies.

🌱 Spring Sprout: springdoc

Spring Boot itself does not create OpenAPI descriptions. A separate library does it: springdoc-openapi. When the application starts, it looks at all your controllers, request and response records, and validation annotations, builds the description, and serves it at /v3/api-docs (JSON) and /v3/api-docs.yaml. The starter with the "ui" in its name also serves Swagger UI at /swagger-ui.html.

Because it is not part of Spring Boot, the Boot parent does not manage its version. You write the version into the pom.xml yourself, and it has to fit your Boot version: springdoc 3.2.0 belongs with Boot 4.1. Official docs: springdoc.org.

Your Task

Add springdoc to the farm API and make the generated description true.

  • Swagger UI opens at /swagger-ui.html and lists every endpoint of the farm.
  • The description has its own title and says 201 for the two POST endpoints that create something.
  • The description lists the error answers (404, 409, 400) as application/problem+json.
  • A test class ApiDocsTest holds each of these facts, so the description cannot silently get worse.

Learning Goals

  • Tell an API description (OpenAPI) from a viewer (Swagger UI)
  • Add a library that Spring Boot does not manage, with an explicit version
  • Read a generated description critically: what it derives correctly, what it gets wrong, what it cannot know
  • Correct a description with a bean and with annotations
  • Test a generated document like any other output of your program

Getting Started

  1. A test for the description (red). Create ApiDocsTest in src/test/java/alpacas/web. The description is built from all controllers together, so this is a test of the whole application, not of a slice: annotate the class with @SpringBootTest, @AutoConfigureMockMvc (org.springframework.boot.webmvc.test.autoconfigure; since Boot 4 a @SpringBootTest brings no MockMvc unless you ask for it) and @AutoConfigureTestDatabase (you know this one from Lesson 18: the tests use the embedded H2). Inject a MockMvcTester and write the first test, apiDescriptionListsThePensEndpoint: GET /v3/api-docs answers 200 and the JSON has a member paths['/pens']. Run it: red with Status = 404. Nobody serves that address yet.
  2. The dependency (green). Add org.springdoc:springdoc-openapi-starter-webmvc-ui in version 3.2.0 to the pom.xml and reload Maven. This time you must write the version: it is not managed by the Boot parent (see the Spring Sprout). Run the test again.
  3. Look before you fix. Start the database (podman compose up -d) and the application, open http://localhost:8080/swagger-ui.html. Notice that the address redirects to /swagger-ui/index.html. Open a few endpoints. Press Try it out on GET /farm, then Execute: the page sent a real request to your application. (Careful: Try it out on POST and DELETE changes your local database. That is fine today. Think about it before you ever see this page on a server with real data.) Now open /v3/api-docs too: that is the description Swagger UI reads. Collect in docs/api-notes.md what you find, in two lists:
    • What it got right without help. Hint for the search: look at the schema of CreateAlpacaRequest and compare it with your validation annotations.
    • What is missing or wrong. Look at the title at the top. Look at what POST /pens says it answers, and compare it with your PenChangesTest. Look for any answer other than success.
    Two more tests for facts that are already true will pass the moment you write them: swaggerUiIsServed (the redirect and the page) and validationRulesShowUpInTheSchema (for example the maximum of fleeceLengthCm). Write them anyway. They are the rules the description must keep.
  4. A title (red, then green). Test apiHasAnOwnTitle: $.info.title is "Fiona's Farm API". Red. springdoc takes the title, description and version from a bean of type OpenAPI (io.swagger.v3.oas.models.OpenAPI) if you provide one. Write a small @Configuration class ApiDocsConfig in alpacas.web with a @Bean method that returns an OpenAPI with an Info (title, description, version). Green.
  5. The status it cannot know (red, then green). Test creatingAPenIsDocumentedAs201: the responses of post on /pens contain 201 and do not contain 200. Red. Why does the generator say 200? It reads the signature of createPen: it returns a ResponseEntity, and "OK" is the default. That the method calls ResponseEntity.created(...) is decided while the method runs; nobody can read that from the outside. You have to tell it. Put @ApiResponse(responseCode = "201", description = "...") (io.swagger.v3.oas.annotations.responses.ApiResponse) on createPen and on createAlpaca. Green: the annotation replaces the default 200.
  6. The errors (red, then green). Test unknownPenIsDocumentedAs404: the responses of get on /pens/{penName}/alpacas contain 404. Red. Your controllers never mention a 404; the translation happens in ApiExceptionHandler. springdoc can read that class: it looks at the @ExceptionHandler methods of a @RestControllerAdvice and uses a @ResponseStatus on them to add the status to the operations. Your handlers return a ProblemDetail that carries its own status, so the annotation is redundant for Spring and only there for the documentation. Add it to every handler method (NOT_FOUND on the two not-found handlers, CONFLICT on the conflict handler, BAD_REQUEST on the other three). Green. Run the **whole** suite: all earlier tests must still pass, because the annotation must not change what really happens.
  7. Look again. Restart the application and reload Swagger UI. The errors are there, with the media type application/problem+json. Look at GET /farm too: it lists 404, 409 and 400 as well, although that endpoint can never answer them. The advice applies to every endpoint. Write that in docs/api-notes.md as a known limit, with the question: is a description that says too much worse than one that says too little?
  8. Commit after each green step.

Acceptance Criteria

Hints

Hint 1

The dependency and the test class with its first two tests:

<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>3.2.0</version>
</dependency>
@SpringBootTest
@AutoConfigureMockMvc
@AutoConfigureTestDatabase
class ApiDocsTest {

    @Autowired
    MockMvcTester mvc;

    @Test
    void apiDescriptionListsThePensEndpoint() {
        assertThat(mvc.get().uri("/v3/api-docs"))
                .hasStatusOk()
                .bodyJson().extractingPath("$.paths['/pens']").isNotNull();
    }

    @Test
    void swaggerUiIsServed() {
        assertThat(mvc.get().uri("/swagger-ui.html"))
                .hasStatus(302)
                .hasHeader("Location", "/swagger-ui/index.html");
        assertThat(mvc.get().uri("/swagger-ui/index.html")).hasStatusOk();
    }
}

Imports: org.springframework.boot.test.context.SpringBootTest, org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc, org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase, org.springframework.test.web.servlet.assertj.MockMvcTester.

Hint 2

Tests that look into the description. A path with special characters goes into ['...']:

@Test
void apiHasAnOwnTitle() {
    assertThat(mvc.get().uri("/v3/api-docs"))
            .bodyJson().extractingPath("$.info.title").isEqualTo("Fiona's Farm API");
}

@Test
void creatingAPenIsDocumentedAs201() {
    assertThat(mvc.get().uri("/v3/api-docs"))
            .bodyJson().extractingPath("$.paths['/pens'].post.responses").asMap()
            .containsKey("201")
            .doesNotContainKey("200");
}

@Test
void unknownPenIsDocumentedAs404() {
    assertThat(mvc.get().uri("/v3/api-docs"))
            .bodyJson().extractingPath("$.paths['/pens/{penName}/alpacas'].get.responses").asMap()
            .containsKey("404");
}

@Test
void validationRulesShowUpInTheSchema() {
    assertThat(mvc.get().uri("/v3/api-docs"))
            .bodyJson().extractingPath("$.components.schemas.CreateAlpacaRequest.properties.fleeceLengthCm.maximum")
            .isEqualTo(10);
}
Hint 3

The title bean, the 201 on the two POST methods, and the status on a handler:

@Configuration
class ApiDocsConfig {

    @Bean
    OpenAPI farmApi() {
        return new OpenAPI().info(new Info()
                .title("Fiona's Farm API")
                .description("Pens and alpacas of Fiona's farm.")
                .version("1.0"));
    }
}
@PostMapping("/pens")
@ApiResponse(responseCode = "201", description = "The pen was created.")
ResponseEntity<PenSummaryResponse> createPen(@Valid @RequestBody CreatePenRequest request) {
    ...
}
@ExceptionHandler(PenNotFoundException.class)
@ResponseStatus(HttpStatus.NOT_FOUND)
ProblemDetail penNotFound(PenNotFoundException e) {
    return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
}

Imports: io.swagger.v3.oas.models.OpenAPI, io.swagger.v3.oas.models.info.Info, io.swagger.v3.oas.annotations.responses.ApiResponse, org.springframework.web.bind.annotation.ResponseStatus. The other five handlers get the same treatment, each with its own status.

When You're Done

Reflect

  • The 201 in the description comes from an annotation you typed. The 201 that really arrives comes from ResponseEntity.created. If you changed the controller to ResponseEntity.ok, which of your tests would fail? Is the description now generated from the code, or only partly?
  • Open the ProblemDetail schema in the description and compare it with a real 400 answer for an invalid alpaca (use Try it out). Where does the description disagree with the real answer? Who would be misled by that, and how could you correct it?
  • Which of these facts did springdoc derive from your code, and which did you have to tell it: the maximum fleece length, which fields are required, the names of the endpoints, the status of a created pen, the error answers? What do the two groups have in common?
  • Ilona asks for the description file so that a program can write the frontend's client from it. Which of your corrections today matters most to her, and why?
  • Swagger UI lets anybody who can reach the address press Try it out. Should it be there on the company's production server? Who would you ask?
  • Names like pen-controller in the tag list come from your class names. What does that say about renaming a class?
