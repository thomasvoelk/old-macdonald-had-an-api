Lesson 20: A Fresh Pair of Eyes

Story

The Angular team starts on Monday. Ilona has been waiting for this API for weeks, and Fiona will watch the first screen on the big monitor. Hasi stops by on Friday afternoon. "Before somebody builds on your API, let somebody who did not write it read it. You cannot do that, you wrote it. But you can come close: read it as if Ilona had written it and you had to use it."

Today you write no feature. You review the farm API, write down what you find, and fix two things.

🚜 Barn Briefing: how to review an API

A review is reading with a question in your head. Reading "does this work?" finds little, because you know that it works: you have tests. Better questions look from outside:

  • The contract. Are things called the same everywhere? Does the same situation always get the same status and the same error shape? Can a client guess an address it has never seen?
  • The client's day. Think of a real screen: the list of alpacas ready to shear with a Shear button. Which calls does it need? Is every piece of information it needs in an answer, or does it have to guess?
  • The edges. What happens with nothing, with too much, with the wrong method, with two requests at the same time, after a restart?
  • The code behind. Which part would you be afraid to change on a Friday? Which names lie? What is left over that nothing uses?

Write every finding down in the same short form: where, what, why it matters to somebody, what you would do. A finding without "why it matters" is a taste, and a review full of taste is hard to act on. Then rank: not everything is worth fixing today.

Your Task

Review your own farm API and fix two of the findings, test-first.

  • A file docs/api-review.md with at least eight findings in the form above, from at least three of the four lenses.
  • The findings are ranked. The top three have a sentence on what you would do about each.
  • Two findings are fixed, test-first, one commit each. At least one of them changes the behaviour of the API, not only a name.
  • The findings you did not fix stay in the file as a list of known limits (Lesson 21 uses them).

Learning Goals

  • Read your own work from the outside, as its user
  • Write a finding that somebody else can act on
  • Rank findings by who is hurt, not by how easy they are to fix
  • Fix a small thing test-first and keep the rest of the suite green

Getting Started

  1. Read it as Ilona. Close your editor. Open only the contract openapi.yaml (Lesson 19). Using only that file, plan the screen "alpacas that are ready to shear, with a Shear button". Write down the calls you would make. Where do you get stuck? That is already your first finding.
  2. Read it as a caller who makes mistakes. Start the application and use docs/requests.http (or curl): ask for a pen that does not exist, send a body with a missing field, use the wrong method on an address, send a body that is not JSON. Compare the answers. Are they all built the same way?
  3. Read the code as a newcomer. Open the controllers, the advice, ShearingService, JdbcPenRepository and the domain package. For each: what would surprise a person who joins tomorrow? What does a name promise that the code does not keep?
  4. Write the review. Create docs/api-review.md. Eight findings or more, each with where, what, why it matters, what I would do. Do not fix anything while you write. If you catch yourself opening a test, write the finding first.
  5. Rank. Put the findings in an order: who is hurt most, and how often? Mark your top three.
  6. Fix two. Pick one small and one that changes behaviour. For each: write the failing test first, watch it fail for the right reason, make it green, run the whole suite, commit. If a fix turns out bigger than an hour, stop, write down why, and pick another one. That is also a finding.
  7. Update the file. Mark fixed findings as fixed (with the commit), and collect the rest under "Known limits".

Acceptance Criteria

Hints

Hint 1: places to look

Not findings, just doors to open:

  • The answer of GET /alpacas/ready-to-shear. Then the address of the shear endpoint. Put them next to each other.
  • The addresses: names in the path, ids in the answers. What can a client do with an id?
  • What PUT does when the address is written in lower case (Lesson 12).
  • Which exception becomes which status (ApiExceptionHandler). What if a bug somewhere else throws one of them?
  • The answer for an address that does not exist, and for a wrong method, compared with your other errors.
  • What GET /farm loads from the database to produce three numbers.
  • What ShearingService keeps in memory, and what happens to it when the application restarts.
  • Two requests that change the same pen at the same moment (Lesson 17, Reflect).
  • Classes and methods nothing calls any more.
  • What is in application.properties, and what the seed job in DatabaseConfig does on a database that is not empty.
Hint 2: some findings other reviewers made

Compare with your list after you wrote it, not before.

  • The ready-to-shear list does not say which pen an alpaca lives in, but the shear endpoint needs the pen name. A client cannot build the button from one call.
  • Ids appear in every answer, but no address accepts one. Names are in the addresses, and a name can be reused in another pen.
  • IllegalStateException always becomes 409 and IllegalArgumentException always 400, wherever they come from. A programming error in a library call would look like the caller's mistake.
  • GET /farm loads every pen with all its alpacas (and does it twice) to count them.
  • The shear log lives only in memory; after a restart the fleece is 0 but nobody remembers who did it.
  • The shepherd's name is written into the code; the map of shepherds in the service is a plain HashMap that many requests use at once.
  • Farm and its test are not used by the web layer any more.
  • An unknown address or a wrong method does not answer in the same shape as your other errors.
  • The contract promises a Problem schema with an errors member, but the handlers build a ProblemDetail by hand. Nothing in the build checks that the two fit.
Hint 3: an optional hard fix, one error shape for everything

If you picked "an unknown address or a wrong method does not answer like the other errors", here is the path I have walked; try the first steps by yourself.

  1. Test first: GET /nothing answers 404 with the content type application/problem+json (MediaType.APPLICATION_PROBLEM_JSON); the same for a GET on a POST address (405). Red: in a test the content type is null.
  2. Spring can answer these standard errors as problems too. Switch it on in application.properties: spring.mvc.problemdetails.enabled=true. The two new tests are green.
  3. Run the whole suite. Two older tests are red: the ones that expect the errors member for an invalid alpaca and for a missing field. The body now says Invalid request content. and has no errors. Spring's own handler for these two exceptions now answers before yours. Read the failure, then think: two handlers for the same exception.
  4. The way out: let your advice be Spring's handler. Make ApiExceptionHandler extend ResponseEntityExceptionHandler and turn your two @ExceptionHandler methods for MethodArgumentNotValidException and HttpMessageNotReadableException into overrides of the methods the base class offers for them. (A second @ExceptionHandler for the same exception in the same class would clash with the base class.)
@Override
protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException e, HttpHeaders headers,
                                                              HttpStatusCode status, WebRequest request) {
    Map<String, String> errors = new LinkedHashMap<>();
    e.getBindingResult().getFieldErrors()
            .forEach(error -> errors.put(error.getField(), error.getDefaultMessage()));
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "The request body is invalid.");
    problem.setProperty("errors", errors);
    return ResponseEntity.badRequest().body(problem);
}

@Override
protected ResponseEntity<Object> handleHttpMessageNotReadable(HttpMessageNotReadableException e, HttpHeaders headers,
                                                              HttpStatusCode status, WebRequest request) {
    return ResponseEntity.badRequest()
            .body(ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "The request body is not valid JSON."));
}

Imports: org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler, org.springframework.http.HttpHeaders, org.springframework.http.HttpStatusCode, org.springframework.http.ResponseEntity, org.springframework.web.context.request.WebRequest. Everything is green again and every error the API can produce has one shape. (The contract from Lesson 19 does not list the unknown-address answer yet. Should it?)

When You're Done

Reflect

  • Which finding would you never have made while you were writing the code? What changed in how you looked?
  • Which of your top three findings was the cheapest to fix, and which the most expensive? Did you rank by that, or by who is hurt? Why is that the right order?
  • One finding came from the screen "ready to shear with a Shear button". Which other screen would you plan to find more gaps?
  • If a colleague wrote the same review about your code on Monday, how would you want the findings to be written?
  • Some of the findings are about things that work. Is "works" the same as "good to use"?
  • Your review touches code from Lessons 02 to 19. Which lesson's decision would you take back today, and which would you keep?
