Lesson 21: What Comes Next

Story

Friday, four o'clock. The big monitor shows Ilona's first screen, and Fiona reads her own farm's name on it and grins. "And the screens? Ilona's screens, they just talk to your program?" Ilona nods. "We wrote the agreement together, as a file, before you wrote the code. I know every address and every answer."

Your part is done. Hasi asks for one more thing: "Leave the farm so that the next person, who is not you, can pick it up without asking. And tell Ilona what the Angular side can rely on, and what it cannot."

🚜 Barn Briefing: what the frontend sees of your work

A browser application knows nothing about Java, Spring, repositories or tables. It sees exactly three things: the addresses, the bodies that go in and come out, and the status codes with their error shape. That is the contract you built in Lessons 02 to 12 and wrote down as a file in Lesson 19. Everything else you learned (the domain, the repository, the database) is the part the frontend is allowed not to know. When you rename a class, Ilona must notice nothing. When you rename a JSON field, she must.

The OpenAPI file from Lesson 19 is the file to give her. Tools exist that read such a file and write the code that calls the API from TypeScript. They are only as good as the file, and your controllers are built from the same file, so the shapes cannot drift apart. What the file cannot promise is behaviour, and that is what your tests are for.

Some things this course did not cover, because they are the next course or the next project: who may call what (login, roles), the rule of browsers that decides which web pages may call your server at all (CORS), changing the database tables in a controlled way when the application grows (migrations), testing against a real PostgreSQL instead of H2, and watching the application when it runs on a server. You will meet all of them at work. You now know where each one would plug in.

Your Task

Hand the farm over: write docs/handover.md and present the whole course result.

  • docs/handover.md is one page for a person who has never seen the project. It answers: how do I start the database and the application, how do I run the tests, where is the API described, what can the API do (one line per endpoint), and what should I know before I change something.
  • The known limits from docs/api-review.md are in the file, in your own words.
  • Your last section is a short list of "what I would do next, in this order", with a sentence of reasons for each.
  • You present the farm to your mentor (the Phase 5 demo, see below).

Learning Goals

  • Write documentation for a reader who cannot ask you
  • Separate what a client may rely on (the contract) from what is yours to change
  • Name what the project still lacks and decide what comes first
  • Explain the whole architecture in your own words

Getting Started

  1. Test the handover before you write it. Clone your repository into a new empty folder (or ask a fellow apprentice to), and follow only your current notes. Where do you get stuck? Write every stumbling stone down. Do you need a Java version, Maven, Podman, a command to start the database? That list is the first half of your handover.
  2. Write docs/handover.md. Short sections, commands in code blocks that you have actually run. Include where the contract lives (src/main/resources/api/openapi.yaml) and how the interfaces and records are generated from it (mvn generate-sources).
  3. The contract. A table with the method, the address, and what it does, one line each. You can take it from openapi.yaml. Check it against the running application: a table you did not verify can be wrong without anybody noticing.
  4. The limits and the next steps. Take your known limits from Lesson 20. Which three would you fix first, and why? You can also think of the big topics from the briefing (login, migrations, a test against real PostgreSQL). Say where in the code each would start.
  5. Check it with a stranger. Give the file to somebody who did not follow the course and watch them use it, without helping. What do they ask? Add the answer to the file.
  6. Prepare the demo. See "Phase 5 demo" below. You do not need slides. You need the running application, the contract file, your tests, and your review.

Acceptance Criteria

Hints

Hint 1

Sections that most handover files need: What this is (two sentences), Run it (database, application, tests), The API (where it is described, the table), How it is built (the packages alpacas and alpacas.web, the repository interface and its two implementations), Limits, Next.

Hint 2

"How it is built" is easier with a picture in words. Draw, in a few lines, the path of one request, for example POST /pens/Ring/alpacas: controller, request record, domain, repository, database. Then do the same for the answer. One path is enough; every other path looks similar.

Hint 3

For "what a client may rely on", ask for each name in a JSON answer: if I rename this, who notices? A field name in an answer: Ilona. A class name: nobody. An error message in detail: perhaps somebody who copied it into a test. Write down what is a promise and what is only today's wording.

When You're Done

Phase 5 demo

Show your mentor, as after every phase:

  • Start the database and the application. Call three endpoints by hand (docs/requests.http or curl): one that reads, one that changes, one that fails. Show where each one is in openapi.yaml.
  • Run the tests and walk through one of them, from the controller down to the database.
  • Pick one design decision from the whole course that you are proud of, and one you would make differently. Explain both in your own words.
  • Walk through your review and your handover file.
  • Answer the Reflect questions below.

Reflect

  • Explain to a friend who knows only Java what the difference is between the domain, the repository and the controller, and why they are separate. Use the farm.
  • Which part of the course would you want to do again? Which one changed how you write code?
  • The frontend now depends on your field names. What would you do to rename one safely?
  • Which of the big topics from the briefing (login, CORS, migrations, real-database tests, monitoring) will your company project need first? How would you find out?
  • What would you tell the next apprentice who starts this course on Monday?
