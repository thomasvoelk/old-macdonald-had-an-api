Lesson 07: Who Is That Alpaca?

Story

Ilona's detail screen shows one alpaca: tap "Lita" in the Ring list. She needs GET /pens/Ring/alpacas/Lita. "And if there is no such alpaca," she adds, "tell me! I can't show an empty page and call it a day."

Your Herd.findByName has a problem: when there is no such alpaca, it returns null. The briefing below says why that matters. The domain may change for the sake of the web code, but test-first.

🚜 Barn Briefing: when nothing is found

Look at what a caller of your current findByName can write, and what a caller of an Optional version can write:

// returns null
Alpaca alpaca = herd.findByName("Nobody");
// compiles, then NullPointerException
alpaca.getWeight();

Optional<Alpaca> found = herd.findByName("Nobody");
// does not compile: Optional has no getWeight()
found.getWeight();

The difference starts in the method's first line, the one a caller reads before using it:

// "give me a name, you get an Alpaca"
public Alpaca findByName(String name)

// "give me a name, you get an Alpaca, or nothing"
public Optional<Alpaca> findByName(String name)

When a method says it returns an Alpaca, you expect an alpaca, so you use the result straight away: alpaca.getWeight(). But sometimes you do not get an alpaca. You get null. That is not obvious from the first line, which says Alpaca and does not always deliver one, and nothing in the code makes you check. You only find out when the program crashes. In a web application that crash reaches Ilona's screen as a 500.

When a method returns an Optional<Alpaca>, the first line tells the truth: the result is a box that either holds an alpaca or is empty. You cannot call getWeight() on the box. First you have to take the alpaca out, for example with orElseThrow(...), and while you write that you also write what should happen when the box is empty. So the empty case cannot slip through unnoticed (Java Lesson 22).

A rule of thumb that fits your whole domain:

  • Many results: return a List, and an empty list when nothing matches. Your getAlpacasReadyToShear() already does this. Never null.
  • One result that may not exist: return an Optional. Never null.

🌱 Spring Sprout: exceptions

When a controller method throws an exception that nobody catches, Spring answers with 500 Internal Server Error: "the server is broken". But "no alpaca by that name" is not the server's fault; it is the request that asked for something that is not there, which is 404 Not Found. A method inside the controller, marked @ExceptionHandler, can catch an exception type and decide the answer. Official docs: @ExceptionHandler.

Your Task

Build GET /pens/{penName}/alpacas/{alpacaName}: 200 with the AlpacaResponse of that alpaca; 404 when the pen exists but has no alpaca by that name.

To get there, change Herd.findByName to return Optional<Alpaca>.

Learning Goals

  • Change a domain method test-first because an adapter pushes back
  • Turn an Optional into either a response or an exception
  • Write a path with two variables
  • Answer a request with 404 using an @ExceptionHandler method

Getting Started

  1. Domain first. In HerdTest, change the existing findByName tests: a found alpaca is Optional.of(alpaca) (or check isPresent()), an unknown name is Optional.empty(). They fail to compile or fail: red. Change Herd.findByName to return Optional<Alpaca>, and let IntelliJ show you every caller that breaks. Fix them, run mvn test, commit as refactor: or feat: as you see fit.
  2. Test first: found. In PenControllerTest: GET /pens/Ring/alpacas/lita answers 200 and $.name is Lita (with the spelling the farm has: the lookup ignores case, the answer is the farm's own data). Make it pass with @GetMapping("/pens/{penName}/alpacas/{alpacaName}"), two @PathVariable parameters, findPen and then findByName.
  3. An exception that means "not found". Look at what Optional offers when it is empty: orElseThrow(...) takes a supplier of an exception. The farm already throws PenNotFoundException for unknown pens; for the alpaca, create AlpacaNotFoundException in alpacas.web (a RuntimeException with a message such as No alpaca named Nobody in pen Ring). Why in the web package and not in the domain? Because today the domain never needs this exception: the request was wrong, not the farm. Write the sentence in docs/api-notes.md and be ready to disagree with it in Phase 4.
  4. Test first: not found. GET /pens/Ring/alpacas/Nobody answers 404. Run it: red, because the exception ends as 500 (or as a thrown exception in the test). Make it green with an @ExceptionHandler method inside the controller: the method gets the annotation @ExceptionHandler(AlpacaNotFoundException.class) plus @ResponseStatus(HttpStatus.NOT_FOUND), and may be empty. Commit.
  5. Check the neighbours. Write the test that you expect to pass: GET /pens/Nowhere/alpacas/Lita answers 404, too. Run it. It does not pass, and that is the topic of the next lesson. Keep the test red (write it down in the notes and commit it as a test: only if your mentor wants you to; otherwise do not commit it yet).

Acceptance Criteria

Hints

Hint 1

The domain test comes first. What does the test for an unknown name look like with Optional? Think of assertTrue(optional.isEmpty()) or AssertJ's assertThat(optional).isEmpty().

Hint 2

In the controller you can chain: pen.getHerd().findByName(alpacaName).map(AlpacaResponse::from).orElseThrow(() -> new AlpacaNotFoundException(alpacaName, penName)). Read it out loud: "find, then map, otherwise throw".

Hint 3

@ExceptionHandler(AlpacaNotFoundException.class) @ResponseStatus(HttpStatus.NOT_FOUND) void alpacaNotFound() {} is a method of PenController. HttpStatus is org.springframework.http.HttpStatus.

When You're Done

Reflect

  • Why is it better for findByName to return an Optional than null for every future caller, not only for this controller?
  • Your @ExceptionHandler lives in PenController. What happens when you later write a second controller that also looks up alpacas?
  • The unknown-pen test is red. Where in the code path does that exception come from, and who throws it?
