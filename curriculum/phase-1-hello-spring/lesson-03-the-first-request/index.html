Lesson 03: The First Request

Story

Fiona's first question for her screens is the simplest one: "What is this farm?" You already have a Farm object that knows exactly that, and Spring can now hand it to a controller. So the quickest way to answer is to return the farm itself. Let's do the simplest thing that could work, and then take a good look at what comes out.

🚜 Barn Briefing: HTTP in two minutes

Before any Spring: what actually happens when a browser, a phone app or curl talks to a server? It is always the same conversation: one request, one response. The server does nothing until a request arrives.

  • A request says what to do and to which resource: a method (GET = "give me") and a URL path (/farm). The server looks for the code that is responsible for exactly that pair, GET /farm.
  • A response says how it went and what came out: a status code (200 = ok, 404 = nothing is responsible for this method and path) and usually a body, here JSON.
  • Both sides also send headers: small labelled extras such as Content-Type: application/json ("the body is JSON"). We mostly ignore them for now.

Here is a real request and response as curl -v http://localhost:8080/farm shows them (lines starting with > were sent, lines starting with < came back):

> GET /farm HTTP/1.1                    request: method + path
> Host: localhost:8080                  request: headers
> Accept: */*
>
< HTTP/1.1 200                          response: status code
< Content-Type: application/json        response: headers
< Content-Length: 44
<
{ ...the body: the farm as JSON... }    response: body

In Lesson 01 you already sent such a request with curl -i and got a 404. Today something answers with 200.

The same four parts reappear in your test:

HTTPIn the test
methodmvc.get()
URL path.uri("/farm")
status code.hasStatusOk(), .hasStatus(404)
body.bodyJson(), .bodyText()

Older tutorials call the body the content (content() matchers, getContentAsString()). It is the same thing.

🌱 Spring Sprout: controllers

A REST API is a program that answers HTTP requests like the one above. In Spring, the code that answers them lives in a controller: a class whose methods are each responsible for one method-and-path pair, such as GET /farm. A controller is a bean, like the farm from Lesson 02. Today you build one controller with one method, and a test that sends it a request. Each step below explains the new words right where you need them.

Official docs: Annotated controllers, Testing Spring Boot applications.

Your Task

Build GET /farm. It answers 200 with JSON for the farm. Keep it as simple as possible: return the Farm object itself from the controller method.

Then look at what comes out. Before you call it the first time, take one minute and write down what you expect the JSON to look like (step 4 below explains how Jackson decides what goes in). You'll compare in a moment.

Learning Goals

  • Write a controller test first with @WebMvcTest and MockMvcTester
  • Build a @RestController with constructor injection
  • Understand how Jackson turns an object into JSON (getters and public fields)
  • Call your own API by hand and read the response critically

Getting Started

  1. Test first: send a fake request.

    A test that sends fake requests to your controller needs three things:

    • @WebMvcTest(FarmController.class) on the test class: it prepares the test for sending fake requests to that controller
    • @Import(FarmConfig.class) on the test class: it loads your farm configuration from Lesson 02, so the controller can get its Farm
    • a field @Autowired MockMvcTester mvc: you ask Spring for it, just like the farm in Lesson 02. Think of it as a fake browser: it plays the client on the left of the picture above. It sends a request to your controller and hands you the response, but nothing is displayed and no real server is started. You check the response with AssertJ, a style you already know. The table above shows which call stands for which part of HTTP

    (In Boot 4, @WebMvcTest lives in org.springframework.boot.webmvc.test.autoconfigure. Older tutorials show a different package.)

    Now write it, in src/test/java/alpacas/web/: a test class with the three things above. Send mvc.get().uri("/farm") and assert the status. It does not compile: FarmController doesn't exist.

  2. Create the controller.

    A controller is a class annotated with @RestController: "this class answers HTTP requests, and what its methods return becomes the response body". Create an empty FarmController with that annotation so the test compiles. The test now fails with a 404: the controller exists, but no method is responsible for GET /farm yet. That is a good red.

  3. Answer GET /farm.

    A method annotated with @GetMapping("/farm") means: "call this method for GET /farm". The method returns a Java object, and Spring turns it into JSON for the response body. The method needs the farm, and it does not build one with new. It asks for it in the controller's constructor. Spring creates the controller by calling that constructor, just like your own new would, and passes in the Farm bean from Lesson 02 as the argument:

    This is called dependency injection: an object receives what it needs instead of building it. You know the idea from the Java course: a Pen gets its Herd through the constructor instead of creating it. Spring just does the handing-over for the whole application.

    Now write it: make the status test pass. Then add one test at a time for the farm's name, its number of pens and the pens themselves, and make each pass. Commit after every green test.

  4. Predict the JSON.

    The conversion from object to JSON is done by a library called Jackson. By default it writes one entry into the JSON for every public getter (getName() becomes "name", isHealthyWeight() becomes "healthyWeight") and for every public field (a variable of the class, also called an attribute, German Attribut). It calls those methods for real, on real objects.

    Now take one minute: look at your Farm, Pen, Herd and Alpaca classes and write down what you expect the JSON to look like.

  5. Start the application and call it by hand: curl http://localhost:8080/farm (Windows PowerShell: curl.exe) or open the URL in a browser. Read every line of the JSON. Watch the console of your running application while you call it.
  6. Create docs/api-notes.md and write down: where was your prediction right, where was it wrong, and what surprised you? Keep it short.

Hints

Hint 1

The test needs three things: an annotation that prepares it for fake requests to your controller, a way to get your farm configuration into it, and a tool to send the fake request. Re-read step 1.

Hint 2

Imports for Boot 4: org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest, org.springframework.test.web.servlet.assertj.MockMvcTester, and AssertJ's assertThat. The pattern is assertThat(mvc.get().uri("/farm")).hasStatusOk(). For a field in the JSON, chain .bodyJson().extractingPath("$.name").isEqualTo(...); $ means "the whole JSON document". To count the entries of a list, use a path like "$.pens.length()".

If the test fails with an exception about a missing bean for Farm, you haven't told the test where the farm comes from. Check your @Import.

Hint 3

The controller: a package-private class annotated @RestController, with a private final Farm farm set by the constructor (no @Autowired needed: one constructor is enough). A method annotated @GetMapping("/farm") with return type Farm returns farm. That's all.

When You're Done

Reflect

  • Did Fiona's screens ask for all of that? Which parts would it never use?
  • Your isHealthyWeight() printed to the console during a request that never asked about health. What does that tell you about how Jackson uses your methods?
  • Does the JSON contain the total number of alpacas on the farm? Where would a client have to look for it?
  • Who now depends on the names getPensCount and getHerd?
