Lesson 03: The First Request

Style for this phase: Chicago (inside-out). We start from the domain you already have and build outwards, one small test at a time.

Story

The phone app's first question is the simplest one: "What is this farm?" You already have a Farm object that knows exactly that, and Spring can now hand it to a controller. So the quickest way to answer is to return the farm itself. Let's do the simplest thing that could work, and then take a good look at what comes out.

HTTP in two minutes

Before any Spring: what actually happens when a browser, a phone app or curl talks to a server? It is always the same conversation: one request, one response. The server does nothing until a request arrives.

  • A request says what to do and to which resource: a method (GET = "give me") and a URL path (/farm). The server looks for the code that is responsible for exactly that pair, GET /farm.
  • A response says how it went and what came out: a status code (200 = ok, 404 = nothing is responsible for this method and path) and usually a body, here JSON.
  • Both sides also send headers: small labelled extras such as Content-Type: application/json ("the body is JSON"). We mostly ignore them for now.

Here is a real request and response as curl -v http://localhost:8080/farm shows them (lines starting with > were sent, lines starting with < came back):

> GET /farm HTTP/1.1                    request: method + path
> Host: localhost:8080                  request: headers
> Accept: */*
>
< HTTP/1.1 200                          response: status code
< Content-Type: application/json        response: headers
< Content-Length: 44
<
{ ...the body: the farm as JSON... }    response: body

In Lesson 01 you already sent such a request with curl -i and got a 404. Today something answers with 200.

The same four parts reappear in your test:

HTTPIn the test
methodmvc.get()
URL path.uri("/farm")
status code.hasStatusOk(), .hasStatus(404)
body.bodyJson(), .bodyText()

Older tutorials call the body the content (content() matchers, getContentAsString()). It is the same thing.

🌱 Spring Corner: controllers, JSON and testing the web layer

A REST API is a program that answers such requests. A controller is a bean whose methods answer them. Two annotations do the work:

  • @RestController on the class: "this is a controller, and what its methods return becomes the response body"
  • @GetMapping("/farm") on a method: "call this method for GET /farm"

The method returns a Java object and Spring turns it into JSON using a library called Jackson. By default Jackson writes one JSON field for every public getter (getName() becomes "name", isHealthyWeight() becomes "healthyWeight") and for every public field. It calls those methods for real, on real objects. The controller gets the Farm through its constructor: that is the dependency injection from Lesson 02.

Testing it. Starting the whole application for every test is slow. @WebMvcTest(FarmController.class) starts only the web layer: that controller, the JSON conversion and the request routing, and no other beans. Inside it you get a MockMvcTester: it sends a fake request to the controller without starting a server and gives you the response to check with AssertJ, a style you already know. Because the slice contains only web beans, you load the farm configuration with @Import(...).

Official docs: Annotated controllers, Testing Spring Boot applications. In Boot 4, @WebMvcTest lives in org.springframework.boot.webmvc.test.autoconfigure. Older tutorials show a different package.

Your Task

Build GET /farm. It answers 200 with JSON for the farm. Keep it as simple as possible: return the Farm object itself from the controller method.

Then look at what comes out. Before you call it the first time, take one minute and write down what you expect the JSON to look like (use the Spring Corner rule for getters and public fields). You'll compare in a moment.

Learning Goals

  • Write a controller test first with @WebMvcTest and MockMvcTester
  • Build a @RestController with constructor injection
  • Understand how Jackson turns an object into JSON (getters and public fields)
  • Call your own API by hand and read the response critically

Getting Started

  1. Test first, in src/test/java/alpacas/web/: a class annotated with @WebMvcTest(FarmController.class) and @Import(FarmConfig.class), with an @Autowired MockMvcTester mvc field. Send mvc.get().uri("/farm") and assert the status. It does not compile: FarmController doesn't exist.
  2. Create an empty FarmController so it compiles. The test fails with a 404: a good red.
  3. Make the status pass. Then add one test at a time for the farm's name, its number of pens and the pens themselves, and make each pass. Commit after every green test.
  4. Start the application and call it by hand: curl http://localhost:8080/farm (Windows PowerShell: curl.exe) or open the URL in a browser. Read every line of the JSON. Watch the console of your running application while you call it.
  5. Create docs/api-notes.md and write down: where was your prediction right, where was it wrong, and what surprised you? Keep it short.

Hints

Hint 1

The test needs three things: a slice annotation that starts only the web layer, a way to get the farm into that slice, and a tool to send the fake request. Re-read the Spring Corner for each.

Hint 2

Imports for Boot 4: org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest, org.springframework.test.web.servlet.assertj.MockMvcTester, and AssertJ's assertThat. The pattern is assertThat(mvc.get().uri("/farm")).hasStatusOk(). For a field in the JSON, chain .bodyJson().extractingPath("$.name").isEqualTo(...); $ means "the whole JSON document". To count the entries of a list, use a path like "$.pens.length()".

If the test fails with an exception about a missing bean for Farm, you haven't told the slice where the farm comes from. Careful: an unrestricted @WebMvcTest loads all controllers, so a missing bean in any of them fails every test in the slice.

Hint 3

The controller: a package-private class annotated @RestController, with a private final Farm farm set by the constructor (no @Autowired needed: one constructor is enough). A method annotated @GetMapping("/farm") with return type Farm returns farm. That's all.

When You're Done

Reflect

  • Did the phone app ask for all of that? Which parts would it never use?
  • Your isHealthyWeight() printed to the console during a request that never asked about health. What does that tell you about how Jackson uses your methods?
  • Does the JSON contain the total number of alpacas on the farm? Where would a client have to look for it?
  • Who now depends on the names getPensCount and getHerd?
