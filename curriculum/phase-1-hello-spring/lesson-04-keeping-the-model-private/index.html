Lesson 04: Keeping the Model Private

Story

Ilona has seen your JSON. "Lovely," she says, "but the start screen only needs three things: the farm's name, how many pens, and how many alpacas. Why am I receiving the whole herd? And why does my screen have to count the alpacas itself?"

Meanwhile Hasi, who cares a lot about good names, reviews your code: "getPensCount() would read better as countPens()." A rename sounds harmless, it is only a name. Try it as an experiment, without committing, and watch what happens to Ilona's screens. Then fix the real problem, and try the same rename again.

Your Task

  1. Feel the coupling first. With IntelliJ's rename refactoring, rename Farm.getPensCount() to Farm.countPens(). IntelliJ fixes all callers. Run mvn test. Which test fails, and why? Nothing about the business changed. Then undo the rename (git restore . or IntelliJ's undo).
  2. Change the contract. GET /farm should answer with exactly {"name": "Fiona's Farm", "pens": 2, "alpacas": 2}: pens and alpacas are plain numbers, and there is nothing else. Do it test-first, with a response record in alpacas.web and the mapping in the controller.
  3. Repeat the rename from step 1. What breaks this time, and where does it break?

Learning Goals

  • Experience that a JSON response is a contract, and what coupling it to the domain costs
  • Explain separation of concerns between domain logic and delivery mechanism
  • Write a response record and map from the domain to it
  • Change a test deliberately because the contract changed

Getting Started

  1. Feel the coupling. Do step 1 of the task. Write two sentences in docs/api-notes.md: what failed, and what that tells you about who owns the name pensCount.

    🚜 Barn Briefing: the domain is not the API

    What you send over HTTP and what you model in Java are two different things, even when they look alike. In Lesson 03 the controller returned a Farm, so Jackson published whatever the Farm happens to look like inside. That was a quick start and a trap, for three reasons:

    • The JSON is a contract. Other programs (Fiona's screens, later an Angular frontend) depend on its field names and shape. A contract should only change when you decide it should.
    • The domain is a model. It describes what the application is all about: the farm, its animals and the rules. You change it whenever the business or your understanding improves: a new study moves the healthy-weight limit, you rename a method, add a field, remove a println. It should be free to change.
    • If both are the same class, every internal change is an API change, and every API wish changes the domain.

    The principle behind this is separation of concerns: domain logic (what an alpaca is, when it is ready to shear) is one concern, the delivery mechanism (HTTP, JSON, status codes) is another. They live in different places and know as little about each other as possible. In this course:

    • the domain classes live in alpacas, and everything web-related lives in its own package alpacas.web
    • a controller never accepts or returns a domain object. Every endpoint has its own response type, a small record, and the controller copies values from the domain into it. This copying is called mapping
  2. Test first. Change the existing tests to describe the new contract: pens is the number 2, alpacas is the number 2. The old pensCount and "list of pens" tests describe the old contract and are replaced. They fail now: pens is still a list and alpacas does not exist. That's your red.
  3. Write the response record.

    A record such as record FarmResponse(String name, int pens, int alpacas) {} becomes {"name":"…","pens":2,"alpacas":2} with no annotations: Jackson writes one entry per record component. (You could also hide fields of the domain class with Jackson annotations, but then your domain class carries delivery concerns, which is exactly what we are avoiding.) Records are Java Lesson 21; official docs: Controller method return values.

    Now write it: make the tests pass with the smallest change, a record and a mapping line in the controller. Commit after every green test.

  4. Start the application and call GET /farm again. Compare with Lesson 03.
  5. Repeat the rename experiment (step 3 of the task). This time it is harmless: you could keep the new name. Undo it anyway, so that your code keeps matching the names used in the next lessons.
  6. Finish docs/api-notes.md: what is better now, and what does it cost you (hint: you wrote a class and a mapping)?

Acceptance Criteria

Hints

Hint 1

Ask yourself: who decides the shape of the JSON now? If it should be decided by the people who use the API, where should the class that describes it live, and should Farm know about it?

Hint 2

You need a new, small class that has exactly the three fields of the new JSON, and nothing else. Java Lesson 21 gives you a one-line way to write such a class. The controller builds an instance from what it asks the Farm. Which Farm methods already give you the name, the number of pens and the total number of alpacas?

Hint 3

Put record FarmResponse(String name, int pens, int alpacas) {} next to the controller in alpacas.web. The controller method's return type becomes FarmResponse and its body is return new FarmResponse(farm.getName(), farm.getPensCount(), farm.totalAlpacas());. The tests for number values use .extractingPath("$.pens").isEqualTo(2).

When You're Done

Phase 1 demo

  • Run the tests and walk through the FarmController test
  • Show the JSON from Lesson 03 next to the JSON from now, and explain in your own words why the controller returns FarmResponse and not Farm
  • Answer the Reflect questions below

Reflect

  • Who owns the name pens in the JSON now, and who owns the name getPensCount? Can they change independently?
  • What did this cost: how many extra lines and classes? Is it worth it for one endpoint? For thirty?
  • Your println in isHealthyWeight() no longer runs during /farm. Is it fixed? Or only hidden from this one endpoint?
  • If the app wants a new field tomorrow, which files change?
