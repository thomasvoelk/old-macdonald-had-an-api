Lesson 04: The First Request

Story

The phone app's first question is the simplest one: "What is this farm, and how big is it?" Time to answer an HTTP request with your own code, test-first, and to find out whether your audit prediction from Lesson 01 was right.

🌱 Spring Corner: controllers, JSON and testing the web layer

A controller is a bean whose methods answer HTTP requests. Two annotations do the work:

  • @RestController on the class: "this is a controller, and what its methods return is the response body"
  • @GetMapping("/farm") on a method: "call this method for GET /farm"

The method returns a Java object, and Jackson turns it into JSON. A record works well for this: record FarmResponse(String name, int pens, int alpacas) becomes {"name":"…","pens":2,"alpacas":2} with no annotations. The controller gets the Farm it needs through its constructor: that is dependency injection from Lesson 03.

The separation-of-concerns rule: a controller never accepts or returns a domain object. It returns its own response type and copies the values over. Why? The JSON is a contract with other programs, the domain is your private model. If they are the same class, you can't change one without the other. This lesson applies the rule for the first time and shows what happens if you break it.

Testing it. Starting the whole application for every test would be slow. @WebMvcTest(FarmController.class) starts only the web layer: the controller, JSON conversion and request routing, but no other beans. Inside it you get a MockMvcTester, a tool that sends a fake request to the controller without starting a server and gives you the response to check with AssertJ, a style you already know. Because the slice contains only web beans, you tell it explicitly which extra configuration to load with @Import(...).

Official docs: Annotated controllers, Testing Spring Boot applications. In Boot 4, @WebMvcTest lives in org.springframework.boot.webmvc.test.autoconfigure. Older tutorials show a different package.

Your Task

Build GET /farm. It answers 200 with JSON containing the farm's name, its number of pens, and its total number of alpacas:

{"name": "Fiona's Farm", "pens": 2, "alpacas": 2}

Use a response record for the JSON, not Farm itself. When it works, do the leak experiment below.

Learning Goals

  • Write a controller test first with @WebMvcTest and MockMvcTester
  • Build a @RestController with constructor injection
  • Return a response record and see Jackson turn it into JSON
  • Understand why a controller doesn't return domain objects, by seeing the damage once
  • Call your own API by hand

Getting Started

  1. Test first, in src/test/java/alpacas/web/: a class annotated with @WebMvcTest(FarmController.class) and @Import(FarmConfig.class), with an @Autowired MockMvcTester mvc field. Send mvc.get().uri("/farm") and assert the status first. It does not compile: FarmController doesn't exist.
  2. Create an empty FarmController so it compiles. The test now fails with a 404. That is a good red.
  3. Make the status pass. Then add one test per JSON field (name, pens, alpacas) and make each pass. One commit per green test.
  4. Refactor: all JSON-field tests use the same request. Can you tidy the test?
  5. Start the application and call it by hand: curl http://localhost:8080/farm (Windows PowerShell: curl.exe), or in the browser. Compare with the test.
  6. Leak experiment (do not commit this): add a throwaway method to the controller that returns a single Alpaca from the farm directly, e.g. Dolly. Start the app, call it, and read the JSON. Compare it with the prediction in your docs/api-audit.md. Watch the application's console while you call it. Then delete the experiment again.
  7. Add a few lines to docs/api-audit.md: what did you predict right, what surprised you?

Acceptance Criteria

Hints

Hint 1

The test needs three things: a slice annotation that starts only the web layer, a way to get the extra bean (the farm) into that slice, and a tool to send the fake request. Re-read the Spring Corner for each.

Hint 2

Imports for Boot 4: org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest, org.springframework.test.web.servlet.assertj.MockMvcTester, and AssertJ's assertThat. The pattern is assertThat(mvc.get().uri("/farm")).hasStatusOk(). For a field in the JSON, chain .bodyJson().extractingPath("$.name").isEqualTo(...). $ means "the whole JSON document".

If the test fails with an exception about a missing bean for Farm, you haven't told the slice where the farm comes from. Careful: an unrestricted @WebMvcTest loads all controllers, so a missing bean in any of them fails every test in the slice.

Hint 3

The controller: a package-private class annotated @RestController, with a private final Farm farm set by the constructor (no @Autowired needed: one constructor is enough). A method annotated @GetMapping("/farm") returns a FarmResponse built from farm.getName(), farm.getPensCount() and farm.totalAlpacas(). The record FarmResponse(String name, int pens, int alpacas) lives next to the controller in alpacas.web. Jackson needs no annotations to turn a record into JSON.

Phase 1 demo

  • Run the tests and walk through the FarmController test
  • Explain in your own words why the controller returns FarmResponse and not Farm. Use your leak experiment as the example
  • Answer the Reflect questions below

Reflect

  • What did a request to your leak-experiment endpoint do besides returning JSON? What does that tell you about getters?
  • Which three layers of your application have you built so far, and which ones are allowed to import Spring?
  • How would a client notice if you renamed FarmResponse.pens? And if you renamed Farm.getPensCount()?
  • Why is it a good thing that the @WebMvcTest starts less than the full application?
