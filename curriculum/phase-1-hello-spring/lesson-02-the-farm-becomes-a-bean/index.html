Lesson 02: The Farm Becomes a Bean

Story

The server is up, but it answers every question with "no idea". It has no farm. Until now, you wrote new Farm("Fiona's Farm") in your tests. In a web application, many requests arrive over time and they all must talk to the same farm. Someone has to create it once and hand it to whoever needs it. In Spring, that someone is Spring.

🌱 Spring Sprout: beans

You know how objects come to life: new Farm("Fiona's Farm") calls the constructor and gives you a new object. Almost everything in your application is still created the way you know: you write new Alpaca(...) and new Pen(...) yourself. But a few objects are special because the whole application shares them. The farm is one of them. Spring takes care of those. An object that Spring creates and keeps for everybody is called a bean. Spring creates it once, and everybody who asks for it gets that same object: one farm, shared by all requests.

Today you do both halves of the picture: first you ask Spring for the farm (in a test), then you teach Spring how to build it. Each step below explains the new words right where you need them.

Official docs: Introduction to the Spring IoC container and beans, Using the @Bean annotation.

Your Task

Let Spring create one Farm named "Fiona's Farm" with two pens: Ring (two alpacas: Lita, 70 kg, 4 cm, white, and Batista, 80 kg, 10 cm, brown) and Cell (empty). Spring has to be taught how to build it; step 2 below shows how.

This is sample data for now. Phase 4 replaces it with a database.

Learning Goals

  • Explain what a bean is and why Spring builds the farm only once
  • Define a bean with a @Configuration class and a @Bean method
  • Explain why Spring needs your code to build the farm
  • Test that a bean exists, with @SpringBootTest and @Autowired

Getting Started

  1. Test first: ask Spring for the farm.

    Remember the three parts of a test from Java Lesson 03: arrange, act, assert. In the arrange part you have always built the objects yourself with new, constructor and all. For an object that Spring manages, that part is taken care of: Spring has already built it. So the arrange part becomes "ask Spring for it". You do that with a field (a variable that belongs to a class, also called an attribute, German: Attribut) and the annotation @Autowired:

    @Autowired
Farm farm;

    @Autowired means: "Spring, fill in this field with the bean of this type." Act and assert stay as you know them: you use the field like any other farm, for example farm.getName(). Two things have to be true for it to work. The test class needs @SpringBootTest, which starts your application first so that the beans exist. And Spring needs to have a Farm bean.

    Now write it: in src/test/java/alpacas/web/, create a test class for your configuration, annotated with @SpringBootTest, with the field above and a test that checks the farm's name. It fails right at the start with an error that says there is no Farm bean. That is your red test.

  2. Teach Spring to build the farm.

    Spring can't invent the farm's name, its pens or its alpacas, so you write the building code yourself. You put it into a configuration class: a class annotated with @Configuration that has a method annotated with @Bean. The method builds the object with plain Java, with the new you already know (new Farm(...), new Pen(...)), and returns it. Spring calls the method once and keeps what it returns. That kept object is the bean from the picture above.

    Now write it: create FarmConfig in alpacas.web and make the first test pass with the smallest configuration you can. (Spring only finds the class if it lives in the right package. The Reflect section at the end lets you try that out.)

  3. Add the second test (the pens) and make it pass.
  4. Look at the fields you used with @Autowired in the test. In production code you will get your dependencies through the constructor instead. Lesson 03 does that.
  5. Commit after every green test.

Acceptance Criteria

Hints

Hint 1

Spring can't invent the farm's name or its pens. So where should the code live that builds the sample farm, and how does Spring learn about it?

Hint 2

Create a class FarmConfig in alpacas.web and annotate it with @Configuration. Give it a method that builds and returns a Farm, annotated with @Bean. The method name becomes the bean's name. Both annotations are in org.springframework.context.annotation. The class and the method can be package-private.

Hint 3

The @Bean method looks like the code you wrote in the Java course: create a Herd, add two Alpacas, create a Farm, add a Pen holding that herd, add a second Pen with an empty herd, return the farm. In the test, a @SpringBootTest class (no arguments) with a field @Autowired Farm farm; is all you need.

When You're Done

Reflect

  • What would go wrong if every request did new Farm(...) itself?
  • Why can't Spring just build a Farm on its own? What does your @Bean method provide that Spring cannot invent?
  • If two classes both ask for a Farm in their constructors, how many farms exist?
  • Try it: move FarmConfig into a new package config outside alpacas and run your test. What happens? Then read why: Spring looks for your configuration classes only in the package of your @SpringBootApplication class (AlpacasApplication, in alpacas) and the packages below it. This is called component scanning. Move FarmConfig back afterwards.
