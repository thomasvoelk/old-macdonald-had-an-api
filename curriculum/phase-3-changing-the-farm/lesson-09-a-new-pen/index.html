Lesson 09: A New Pen

Story

Fiona is standing in front of the barn with her iPad. "I have bought a small stable behind the house, and I want a pen for it. Can I add it myself, right here, without calling you?" Ilona has already drawn the screen: one text field, one button. "I send the name to the server," she says. "What do I get back?"

Phase 3 is about changing. Until now every request only looked at the farm. From here on a request changes it, and that brings new questions: what does the client send, what does it get back, and what if the change is not allowed?

🚜 Barn Briefing: four verbs and their answers

In Lesson 03 a request was a method plus a path. So far the method was always GET. HTTP has a few more, and each has a job. A request that changes something usually carries a body too, just as a response does: the data for the change, here JSON.

MethodMeansUsed in
GETgive me this, change nothingPhase 2
POSTcreate a new thing; the server decides where it livesLessons 09, 10
PUTreplace the thing at this pathLesson 12
DELETEremove the thing at this pathLesson 12

The answer has a status code, and for changes the code says more than 200. These are the ones this phase uses:

StatusMeans
201 Createddone, and there is a new thing now. The Location header (a header is a labelled extra, see Lesson 03) says where it lives
204 No Contentdone, and there is nothing to send back
400 Bad Requestthe request itself is wrong
404 Not Foundthe thing you addressed does not exist
409 Conflictthe request is fine, but the farm is in a state where it cannot be done

All of them are listed in the MDN status code reference. This lesson uses 201 and 409; the others follow.

🌱 Spring Sprout: request-body

A method annotated with @PostMapping answers POST requests, the way @GetMapping answers GET. A parameter annotated with @RequestBody receives the body of the request: Jackson (Lesson 05) reads the JSON and builds an object from it, here a record. To choose the status and the headers yourself you return a ResponseEntity instead of the plain object. Official docs: @RequestBody and ResponseEntity.

Your Task

Build POST /pens. The client sends the name of the new pen:

{"name": "Stable"}

The farm then has a third pen, and the answer is:

  • 201 with the header Location: /pens/Stable
  • a body in the same shape as one entry of GET /pens: {"name":"Stable","alpacas":0}

A pen name can only be used once, ignoring upper and lower case. Posting ring while Ring exists answers 409 with a problem body whose detail says so.

Learning Goals

  • Write a POST endpoint that reads a JSON body into a request record
  • Answer 201 with a Location header
  • Test a request with a body in MockMvcTester
  • Understand that tests share one farm, and what to do about it
  • Find the right place for a new rule (domain) and the right place for its HTTP meaning (advice)

Getting Started

  1. Start red. Add a new test class PenChangesTest in alpacas.web (same annotations as your PenControllerTest) and write the test for 201. The request in MockMvcTester needs two things beside the path: the header that says the body is JSON, and the body itself. 
    mvc.post().uri("/pens")
        .contentType(MediaType.APPLICATION_JSON)
        .content("""
                {"name": "Stable"}""")
    This is your fake browser sending a POST. Add the assertions: status 201, the Location header, and the member alpacas in the body.
  2. Make it green. Three things are new. First, a record CreatePenRequest with the one component name: it is the contract for what the client sends, the counterpart of your response records (Lesson 04, same rule: no domain object in the controller signature). Second, a method with @PostMapping("/pens") whose parameter is annotated with @RequestBody. Third, it returns a ResponseEntity, built with ResponseEntity.created(location).body(...), where location is a URI. Map the request to a domain Pen with an empty Herd, add it to the farm and answer with the same PenSummaryResponse that GET /pens uses.
  3. Tests share one farm. Let the first test also check, after the post, that GET /pens has three entries. Then add a second test that creates "Stable" and checks the same (call it aNewPenAppearsInTheList). Run the class. Each test passes alone, and together the one that runs second is red: the farm has four pens, not three. Why? Your Farm is a bean (Lesson 02), and a bean is created once; Spring keeps the application context between the tests of a class, and every request, in a test or a real one, reaches the very same Farm object. The first test left "Stable" in it. Tell Spring to throw the context away after each test method and build a fresh farm: 
    @DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_EACH_TEST_METHOD)
    on PenChangesTest. It makes the class slower, which is why your reading tests stay in their own class without it. (The same sharing is true of the running application: all clients change one farm, and two requests at the same moment could trip over each other. A database in Phase 4 takes this job over.)
  4. The name can be used only once. Write the test: post {"name": "ring"} and expect 409 and application/problem+json. It stays red, because your domain happily adds a second "Ring". Rules about the farm belong in the domain, so go one level down and write a FarmTest first: adding two pens whose names differ only in case throws an IllegalStateException. Make that green in Farm.addPen, commit, and go back to the controller test.
  5. Who says 409? The domain knows nothing about HTTP; it throws IllegalStateException. The controller test is still red, because nobody translates that exception. You know the place from Lesson 08: add a handler for it to ApiExceptionHandler that answers 409 with a ProblemDetail. The test turns green without touching the controller.
  6. Try it for real. Typing JSON into curl on Windows is a quoting nightmare. IntelliJ can send requests from a plain file: create docs/requests.http with 
    POST http://localhost:8080/pens
Content-Type: application/json

{"name": "Stable"}
    and click the green arrow next to it while the app is running. Send it twice. Compare with the output below, which was captured from a running reference solution with curl -si: 
    HTTP/1.1 201
Location: /pens/Stable
Content-Type: application/json

{"name":"Stable","alpacas":0}

HTTP/1.1 409
Content-Type: application/problem+json

{"detail":"There is already a pen named Stable","instance":"/pens","status":409,"title":"Conflict"}
    The farm lives in memory, so a restart brings back Ring and Cell only. Write a sentence in docs/api-notes.md: why does Ilona's screen care about the Location header?

Acceptance Criteria

Hints

Hint 1

Think about which class does what. The request record is the contract for the incoming JSON, the controller turns it into a domain object, the domain enforces the rule "one name per pen", and the advice decides what an exception means for the client. Where would the check for the duplicate name not belong?

Hint 2

For the controller you need three annotations: @PostMapping("/pens") on the method, @RequestBody in front of the parameter, and in the return type a ResponseEntity<PenSummaryResponse>. ResponseEntity.created(uri) sets the status 201 and the Location header; .body(...) adds the body. For the 409, @ExceptionHandler(IllegalStateException.class) in the advice, and HttpStatus.CONFLICT.

Hint 3

record CreatePenRequest(String name) {}. In the controller: Pen pen = new Pen(request.name(), new Herd()); farm.addPen(pen); return ResponseEntity.created(URI.create("/pens/" + pen.getName())).body(new PenSummaryResponse(pen.getName(), pen.totalAlpacas()));. In Farm.addPen: loop over the existing pens and throw new IllegalStateException("There is already a pen named " + pen.getName()) if equalsIgnoreCase matches. The handler: ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.getMessage()).

When You're Done

Reflect

  • The advice now turns every IllegalStateException into a 409. Is that always right? Think of a bug somewhere in the domain that throws one by accident.
  • The name goes into the URL: /pens/Stable. What happens to the Location header for a pen called Big Barn? (Lesson 10 shows it.)
  • Nothing stops the client from sending {"name": ""} or no body at all. What would you expect the API to answer? What does it answer now? (Lesson 11.)
