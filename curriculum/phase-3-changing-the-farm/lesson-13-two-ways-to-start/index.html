Lesson 13: Two Ways to Start

Story

Fiona has a new wish. "In spring every alpaca gets shorn. Right now I would have to look up each fleece and send you a new length. I want a button on Ilona's screen that says Shear, and then the fleece is gone and the farm remembers who did it."

Before you start, Hasi stops by. He has watched you work for four lessons. "You always begin in the same place," he says. "Domain first, controller last. Did you decide that, or did it just happen? Because there is another way to begin, and the next lesson uses it. Let's look at both before you pick up the keyboard."

This lesson has no code. It is a map for the next one, and for every feature you build after this course.

🚜 Barn Briefing: Chicago and London

Every new feature has the same problem: there is a lot to build, and you have to write one test first. Where do you start? Two answers are famous enough to have names. Both are test-driven. They differ in where the first test goes.

Inside-out (the "Chicago" style). Start with the piece that needs nothing else, usually the domain. You test it with real objects and check what is true afterwards: the herd has one alpaca less, the fleece is 0 cm. When that works, you build the next piece around it, and the controller, the piece the outside world touches, comes last. This is what you did in Lessons 09 to 12: Farm.addPen rejected duplicates and Herd.removeByName existed before any controller used them.

Outside-in (the "London" style). Start at the edge where the request arrives, with a controller test. The controller needs help from something that does not exist yet, say a class that does the shearing. You do not build it now. You write a stand-in for it (a mock, you meet it in the next lesson), tell the stand-in what to answer, and make the controller test pass. That test has just told you what the missing class must be called, what it takes and what it returns. The missing class becomes your next test, and you work inwards until nothing is a stand-in any more.

Inside-out (Chicago)Outside-in (London)
First testthe piece with no helpers, e.g. Herdthe edge, e.g. the controller
Helpers in a testreal objectsstand-ins (mocks) for what does not exist yet
A test checksthe result: what is true afterwardsthe conversation: who is asked what
Strengthsolid pieces; tests survive refactoringyou build only what the outside needs; the design of the inner classes comes out of the use
Riskyou build a piece that the upper layers then do not need, or need differentlytests know how classes talk to each other, so changing a method name breaks tests that did nothing wrong

Neither is "the correct one". Many teams mix them: outside-in when a feature is new and nobody knows what the inner classes should look like, inside-out when the rules are clear and the domain is the interesting part. The names come from where their best-known teachers worked: the London style grew in the London extreme programming scene (the book Growing Object-Oriented Software, Guided by Tests describes it), the Chicago style is the classical way test-driven development was first taught.

Your Task

No code today. You will look at your own work through the two styles, and make a prediction that the next lesson checks.

  • Find out which style you used in Lessons 09 to 12, and where it paid off or hurt.
  • Plan the shear feature both ways on paper, before you see how Lesson 14 does it.

The feature, so that you have something concrete: POST /pens/{penName}/alpacas/{alpacaName}/shear takes all the fleece off one alpaca (fleece length 0), the shepherd of the pen writes a log entry, and the answer is the alpaca as it looks afterwards. You already own most of the pieces in your domain: Alpaca.shear(), Shepherd.shear(alpaca), Farm.findPen. What you do not have is a piece that finds the pen, finds the alpaca and hands it to a shepherd. Who should be that piece?

Learning Goals

  • Describe inside-out and outside-in, and say where the first test goes in each
  • Recognise that Lessons 09 to 12 were inside-out
  • Name one strength and one risk of each style
  • Know that an optional, longer course exists on exactly this question

Getting Started

  1. Read your own history. Run git log --oneline in your repository and look at the commits of Lessons 09 to 12. For each lesson, write one line in docs/api-notes.md: was the first red test in the domain (HerdTest, FarmTest) or at the edge (PenChangesTest)? Where a lesson had both, which came first?
  2. Plan the shear feature inside-out. Write down the first three tests you would write if you started at the domain. Which class do they test? Then write down the place where you get stuck: at some point someone must find the alpaca in the right pen and let a shepherd shear it. Which class does that, and in which package does it live? Write your guess, even if it is a poor one.
  3. Plan it outside-in. Write down the first test you would write if you started at the controller: which address, which answer? Then list what that controller would need from somebody else, in one sentence. You do not have to name the class yet.
  4. Keep your two plans. Do not tidy them up. In the next lesson you build the feature outside-in; afterwards you compare the result with your plans, and the comparison is the point.

🧭 Side Quest (optional)

If these two styles caught your interest, there is a much longer course on exactly this: Clean Coders' Comparative Design builds the same application twice, once outside-in and once inside-out, and compares the results. It is 14 episodes of about an hour; the first five show the London style with Sandro Mancuso. Nothing in this course depends on it, and there are no episodes to watch for the next lesson. Look at it when you want to, or never.

When You're Done

Reflect

  • Your domain tests in Lessons 09 and 12 never needed a mock. Why not? What did the tests use instead of stand-ins?
  • Inside-out, you decide the shape of an inner class (name, parameters, return value) before you know who will call it. Outside-in, the caller decides. Which of the two would you trust more when you do not yet understand the problem?
  • A test that checks who was asked what breaks when you rename the method that was asked, even if everything still works. A test that checks the result does not. Which kind would you rather maintain for two years?
  • Which style would you use to fix a bug in Herd? Which for a brand-new screen Ilona has just sketched?
