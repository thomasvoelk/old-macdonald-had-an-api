Lesson 11: Say No Politely

Story

Fiona's first week with the form. She typed a weight of minus five, left the name empty, and once chose a colour that is not on the list. Your notes from Lesson 10 say what happened: a 500, a new alpaca without a name, a 500 again. Ilona is not happy. "When a field is wrong I want to mark that field in red, and I want to know about all wrong fields at once. Not one error per tap."

Hasi reads the same notes: "A 500 means we broke. Here the client sent something wrong. That is a different status, and a different promise."

🚜 Barn Briefing: 400, 404 or 409?

Three answers say "no", and they say it for different reasons. Ask one question: would this very request be fine on another day, with the farm in another state?

StatusThe request...Example from the farm
400is wrong in itself. It would never workempty name, weight -5, colour PURPLE, broken JSON
404points at something that is not therepen Nowhere, alpaca Nobody
409is fine, but the farm's current state does not allow it. Another day it could workname already taken, pen full

A 500 is a different story: nobody expected it, and the client cannot fix it. Your goal for this lesson is that bad input never reaches that point.

🌱 Spring Sprout: bean-validation

You describe what a valid request looks like with annotations on the components of the request record, such as @NotBlank, @Positive, @Min and @Max. Putting @Valid in front of the @RequestBody parameter makes Spring check them before your method runs; if something is wrong, your method never starts and Spring throws a MethodArgumentNotValidException that lists every violation. Your advice from Lesson 08 turns that into the answer. The annotations come with their own starter (spring-boot-starter-validation), and are called Jakarta Bean Validation. Official docs: Validation in Spring Boot and Java Bean Validation.

Your Task

Make bad input answer 400, as a problem body that names every wrong field.

  • A body with a blank name, a negative weight and a fleece length of 11 answers 400, application/problem+json, and a top-level member errors with one entry per wrong field, for example {"detail":"The request body is invalid.","instance":"/pens/Cell/alpacas","status":400,"title":"Bad Request","errors":{"weight":"must be greater than 0","fleeceLengthCm":"must be less than or equal to 10","name":"must not be blank"}} (the order of the entries inside errors may differ on your machine)
  • A missing field is an error too: no fleeceLengthCm gives "fleeceLengthCm": "must not be null"
  • An unknown colour answers 400 with the detail Unknown fleece color: PURPLE
  • A body that is not JSON at all answers 400, also as problem+json
  • Creating a pen with a blank name answers 400 too

Learning Goals

  • Declare validity rules on a request record and switch them on with @Valid
  • Collect all violations into one answer
  • Know why request records use boxed types (Double, Integer)
  • Tell 400, 404 and 409 apart
  • Understand that a rule can exist twice (at the door and in the domain), and why

Getting Started

  1. Add the starter. In your pom.xml add spring-boot-starter-validation (group org.springframework.boot, no version: the parent knows it) and reload Maven. It brings the annotations and the library that checks them; Spring finds that library by itself.
  2. Start red: all errors at once. Test: post to Cell with {"name": " ", "weight": -5, "fleeceLengthCm": 11, "fleeceColor": "BLACK"}. Expect 400, the content type APPLICATION_PROBLEM_JSON and $.errors.length() equal to 3. It is red: you get 201 or an exception, depending on which part of your code looks at the body first.
  3. Describe the rules. On the components of CreateAlpacaRequest: @NotBlank for the name and the colour, @Positive for the weight, @Min(0) and @Max(10) for the fleece length. Then put @Valid in front of the @RequestBody parameter. Run the test: now the exception is a MethodArgumentNotValidException, and nobody answers it yet.
  4. A missing field. Write the test: leave out fleeceLengthCm and expect $.errors.fleeceLengthCm to be must not be null. Red, and not for the reason you think: with int fleeceLengthCm the record cannot hold "missing". Jackson fills a missing int with 0, and nobody ever knows that the client forgot it. Change the numeric components to the boxed types Double and Integer (they can be null) and add @NotNull. The domain wants plain numbers, so toAlpaca() unboxes them. Why is that safe now?
  5. Answer the exception. In ApiExceptionHandler add a handler for MethodArgumentNotValidException. It returns a ProblemDetail with status 400 and the detail "The request body is invalid.". The violations come from e.getBindingResult().getFieldErrors(): each has getField() and getDefaultMessage(). Collect them into a Map<String, String> and attach it with problem.setProperty("errors", map); ProblemDetail writes it as a top-level member.
  6. The other 400s, one test each. (a) The colour PURPLE: the exception comes from your FleeceColors.parse and from the domain (IllegalArgumentException, FleeceColorNotFoundException). Handle both as 400 and let detail carry the message. (b) A body like { this is not json never reaches your method: Spring throws HttpMessageNotReadableException. Give it a handler with a fixed message such as "The request body is not valid JSON." (do not pass on the exception text, it may mention internals). (c) CreatePenRequest: add @NotBlank and @Valid there too and test a blank pen name.
  7. Look at the table. Go through Lessons 09 and 10 and write, for every test of yours that expects an error, the status and the reason, using the question from the Barn Briefing. Does any test have the wrong status? Put the list in docs/api-notes.md. Then send the three bad requests from the experiment in Lesson 10 against the running app and compare with your notes from back then.

Acceptance Criteria

Hints

Hint 1

Two pieces have to work together: something that declares what valid means, and something that checks it. Which of them is an annotation on the record, and which is an annotation on the controller parameter? And who finally answers when the check fails?

Hint 2

Imports come from jakarta.validation.constraints.* and jakarta.validation.Valid. A record with annotations looks like record CreatePenRequest(@NotBlank String name) {}. For several rules on one component, just put them next to each other: @NotNull @Min(0) @Max(10) Integer fleeceLengthCm.

Hint 3

@ExceptionHandler(MethodArgumentNotValidException.class) ProblemDetail invalidBody(MethodArgumentNotValidException e) { Map<String, String> errors = new LinkedHashMap<>(); e.getBindingResult().getFieldErrors().forEach(error -> errors.put(error.getField(), error.getDefaultMessage())); ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "The request body is invalid."); problem.setProperty("errors", errors); return problem; }. The controller parameter: @Valid @RequestBody CreateAlpacaRequest request. The test: .bodyJson().extractingPath("$.errors.length()").isEqualTo(3).

When You're Done

Reflect

  • The limit "fleece length at most 10" now exists twice: as @Max(10) in the request record and as a check in the Alpaca constructor. Why keep both? What happens to a client that only breaks the domain rule? And how many places do you touch if Fiona's vet says 12 is fine?
  • The handler for IllegalArgumentException answers 400 for any such exception from the domain. A bug in your own code that throws one by accident now also looks like the client's fault. What could you do about it?
  • The message must be greater than 0 is English and written by a library. Who should decide the wording that Fiona sees: the API or Ilona's screen?
