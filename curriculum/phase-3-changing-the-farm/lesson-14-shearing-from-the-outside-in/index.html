Lesson 14: Shearing from the Outside In

Story

Spring has come and Fiona wants her Shear button. Ilona has drawn it next to every alpaca. "It sends one request and shows the alpaca again, so I can see the fleece is gone," she says. "There is nothing to type, so the request has no body."

Hasi reads the ticket over your shoulder. "Your Shepherd class already writes a log entry when it shears. Make sure the log really gets written, otherwise Fiona will ask who sheared Triple H and nobody will know."

Last lesson you made two plans. Today you build the feature outside-in, starting at the controller, and see what the test tells you about the rest.

🚜 Barn Briefing: an action on a thing

So far every request either looked at a thing (GET), made a new one (POST), replaced one (PUT) or removed one (DELETE). Shearing is none of those: the alpaca stays, it just changes in a way that has a name. For such actions a common choice is a POST to a sub-address named after the action: POST /pens/Ring/alpacas/Lita/shear. It has no body, because the address says everything, and it answers 200 with the alpaca as it is now. It is not PUT (that would need the new values) and not 201 (nothing was created). Doing it twice is allowed; the second time there is simply no fleece left to take.

🚜 Barn Briefing: a stand-in for a class that does not exist yet

A mock is an object that a library (Mockito) builds for you at runtime. It looks like the class you ask for, but it has no real behaviour. You tell it what to answer (given(...).willReturn(...), or willThrow(...) for an exception), and afterwards you can ask it what happened to it (verify(...): "was shear called with Ring and Lita?").

In an outside-in test the mock stands in for a class you have not written. The test says: "when the controller asks the service to shear Lita in Ring, the service answers with this alpaca." The controller test can now go green even though the service does nothing. That is the trick, and also the danger: the test only proves that the controller does its own job (it reads the address, asks, turns the answer into JSON). It cannot prove that the service works. You will write a second test for that.

🌱 Spring Sprout: services and test stand-ins

A controller should only deal with HTTP: read the address and body, turn the answer into a response. The real work belongs in a class of its own, and Spring has a name for it: put @Service on it and, like a controller, Spring finds it, creates one object and hands it to every class that asks for it in its constructor. (@Service does exactly what @Component does; the name only tells the reader what the class is for.)

In tests there is a catch. @WebMvcTest starts only the web part of your application: controllers, the exception handler, JSON. It does not create services. A controller that needs a service therefore cannot start in that test unless you provide one. @MockitoBean on a field of the test class says: put a mock of this type into the test's Spring context, and the controller receives it. Official docs: @MockitoBean, @Service and scanning.

Your Task

Build POST /pens/{penName}/alpacas/{alpacaName}/shear:

  • success: 200, body in the shape of AlpacaResponse, fleeceLengthCm is 0
  • the pen's shepherd writes one log entry: Paul Heyman sheared Lita on 2026-11-06 (his name, the alpaca, today's date; that is what your Shepherd already does)
  • unknown pen or unknown alpaca: 404, and nothing is written to the log

Work outside-in: the first test is a controller test, and the class that does the shearing appears because that test needs it.

Learning Goals

  • Start a feature at the controller and let the test discover the next class
  • Use @MockitoBean, given(...).willReturn(...), willThrow(...) and verify(...)
  • Put the work in a @Service and keep the controller to HTTP only
  • Test the discovered class on its own with plain JUnit, no Spring and no mock
  • Say what a controller test with a mock proves, and what it does not

Getting Started

  1. Start red, at the edge. Create ShearingControllerTest in alpacas.web, annotated with @WebMvcTest(ShearingController.class), with MockMvcTester as always. Add a field @MockitoBean ShearingService shearingService. The test: tell the mock that shear("Ring", "Lita") answers an Alpaca with 0 cm of fleece, then POST /pens/Ring/alpacas/Lita/shear and expect 200 and $.fleeceLengthCm equal to 0. Add a verify that the service was asked exactly that. Do not write any production class first.
  2. Let the compiler lead. Your IDE now shows red at two names: ShearingController and ShearingService. You have just invented a class by writing the test. Let the IDE create both in alpacas.web. Mark the controller @RestController and the service @Service. Look at the line with given(shearingService.shear("Ring", "Lita")): it has already decided that the service has a method shear with two strings that returns an Alpaca. Create that method; its body can throw an UnsupportedOperationException for now. Run the test. It is red because there is no mapping yet: Status = 404.
  3. Green: the controller. Give ShearingController a constructor that takes the service, and a method with @PostMapping("/pens/{penName}/alpacas/{alpacaName}/shear") and two @PathVariables. It asks the service and returns AlpacaResponse.from(...). Controllers still never return domain objects. Run the test: green. Look at what you did not write: no shepherd, no farm, no fleece. The controller does not know how shearing works.
  4. Look: what a mock does for the context. Delete the @MockitoBean line and run the test. The error text starts with UnsatisfiedDependencyException: Error creating bean with name 'shearingController'. Why? (The Spring Sprout says it.) Put the line back. Write the cause in docs/api-notes.md.
  5. Two more tests, green at once. Make the mock throw: PenNotFoundException for shear("Nowhere", "Lita"), and AlpacaNotFoundException (from Lesson 07) for shear("Ring", "Nobody"). Expect 404; for the second also check that $.detail is No alpaca named Nobody in pen Ring. Both are green without any new code, because your ApiExceptionHandler from Lesson 08 turns the exceptions into 404. Careful: you did not test that the service throws these. You told a mock to throw them, and only tested that the controller reacts correctly.
  6. Move inwards: the service. The service is still empty, and the next test is its own. Create ShearingServiceTest, plain JUnit like your domain tests: no Spring, no Mockito, real objects. In a @BeforeEach build a Farm with a pen Ring containing Lita and give it to new ShearingService(farm). Make the constructor take the Farm; the test has just decided that. Write the tests one by one, red-green each:
    • shear("Ring", "Lita") returns an alpaca called Lita with fleece length 0.
    • The shepherd writes a log entry: Paul Heyman sheared Lita on <today>. The test needs a way to read the log, so the service gets a method logOf(String penName). Use LocalDate.now() in the expected text, and try the call with "ring" and "lita" in lower case.
    • An unknown pen throws PenNotFoundException.
    • An unknown alpaca throws AlpacaNotFoundException and nothing is logged.
    The snag: look at the constructor of your Shepherd. It needs a Pen, so a shepherd belongs to exactly one pen and keeps the log of that pen. The service cannot make a new shepherd for every request, or the log would be empty each time. It must keep one shepherd per pen. (How? A Map. Which key, when Ring and ring are the same pen?)
  7. Connect the real pieces. The controller test uses a mock and the service test needs no controller. Nobody has yet checked that they fit. Write one test with the real service in ShearingWithRealServiceTest: @WebMvcTest(ShearingController.class) plus @Import({FarmConfig.class, ShearingService.class}), so the slice is allowed to create the service and the farm. In the test @Autowired Farm farm, build your own pen Barbershop with Triple H (85.5 kg, 9 cm, black) straight in the domain, add it to the farm, and POST the shear. Never shear Lita or Batista in a test: other tests read them. A name with a space does not go well into a hand-written path here; hand the parts to the template form: mvc.post().uri("/pens/{pen}/alpacas/{alpaca}/shear", "Barbershop", "Triple H"). Expect 200 and, on the herd you built yourself, fleece length 0. Then one more: /pens/Ring/alpacas/Nobody/shear answers 404.
  8. Try it for real (docs/requests.http): shear Lita, then look at GET /pens/Ring/alpacas. Shear her again. Shear Nobody. Restart the app and look at Lita again; where is her fleece, and where is the log?

Acceptance Criteria

Hints

Hint 1

The imports for the first test: org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest, org.springframework.test.context.bean.override.mockito.MockitoBean, static org.mockito.BDDMockito.given and static org.mockito.Mockito.verify. The mock set-up reads like a sentence: given(shearingService.shear("Ring", "Lita")).willReturn(new Alpaca("Lita", 70, 0, FleeceColor.WHITE));. For the exceptions use .willThrow(new AlpacaNotFoundException("Nobody", "Ring")) instead of willReturn.

Hint 2

The controller method: AlpacaResponse shear(@PathVariable String penName, @PathVariable String alpacaName) { return AlpacaResponse.from(shearingService.shear(penName, alpacaName)); }. Service and controller can be package-private classes: they live in the same package as the test, so Mockito can mock the service.

Hint 3

The service: find the pen with farm.findPen(penName) (it throws PenNotFoundException itself), then pen.getHerd().findByName(alpacaName).orElseThrow(() -> new AlpacaNotFoundException(alpacaName, penName)), then let the pen's shepherd shear. Look the shepherd up before shearing, so nothing is logged when an exception was thrown earlier. For the map: Map<String, Shepherd> keyed by the lower-cased pen name, and computeIfAbsent creates the shepherd for a pen the first time you need it.

When You're Done

Reflect

  • The first test forced the names ShearingService and shear(String, String) on you. Is that where your inside-out plan from Lesson 13 put the missing piece? Would you have chosen the same two strings as parameters, or a Pen and an Alpaca?
  • The controller test is green while the service is empty. Which test would have caught a service that forgets to write the log entry? Which one would catch a controller that forgets to pass the alpaca name?
  • Rename ShearingService.shear to shearOff with the IDE's rename. Which tests change by themselves, which break? What does that say about tests that check who is asked what?
  • The service keeps its shepherds in a HashMap, and Spring creates only one service for the whole running app. Two requests for two different pens arrive at the same moment. What could go wrong? (The farm itself has the same problem; both are fixed properly only with a database.)
  • The shepherd's name Paul Heyman is written into the service. When Fiona hires a second shepherd, which classes have to change?
  • Could the controller have done all of it and skipped the service? What would be harder to test?
