Lesson 17: The Repository Becomes a Table

Story

Fiona restarted the server yesterday, to install an update. "My new alpaca Triple H is gone," she says. "And Lita's fleece is long again. Does your program forget everything when it sleeps?"

It does. The repository from Lesson 15 is a list inside the running program, and a list in memory disappears with the program. Hasi smiles. "You made the repository an interface for exactly this day. Write a second repository that keeps its alpacas in tables, like you did in the SQL course. The interface stays, the contract test stays, and the controllers never find out."

Today you write that second repository, JdbcPenRepository, and you prove it with the same contract test that already proves the in-memory one. The running application does not use it yet. That is Lesson 18.

Barn Briefing: objects and rows

A Pen in memory is an object that holds a Herd that holds Alpaca objects. A database knows none of that. It knows rows in tables: a row in pens, rows in alpacas, and each alpaca row carries the id of its pen (pen_id, a foreign key). Saving means turning the objects into rows. Reading means turning rows back into new objects: copies, not the objects you saved. A change to such a copy is only stored when you call save again.

The general name for turning objects into rows and rows back into objects is object-relational mapping (ORM). In this lesson you do it by hand, with SQL you write yourself. Tools such as JPA and Hibernate do it for you; many projects use them, but not this course.

🌱 Spring Sprout: JdbcClient and @JdbcTest

JdbcClient is Spring's small helper for plain SQL over JDBC. You hand it a SQL text with named parameters (:name), you fill them with .param("name", value), and you end with .update() for insert/update/delete, or with .query(...) for select. Spring Boot creates one JdbcClient bean for you as soon as a database connection (a DataSource) exists, so a class can ask for it in its constructor like for any other bean. It keeps you close to the SQL you already know; it is not an ORM (see the briefing above) that writes the SQL for you. Official docs: JdbcClient.

@JdbcTest is the test annotation for this layer. Like @WebMvcTest for the web, it starts only a small slice of the application: a database, a JdbcClient, and nothing else. By default it replaces your database with an embedded one (H2, a small database that lives inside the test's own process and needs no installation), it runs a file named schema.sql from src/main/resources on it to create the tables, and it wraps every test in a transaction that is rolled back at the end. Official docs: test slices.

Your Task

Write JdbcPenRepository implements PenRepository in package alpacas, backed by two tables, and prove it with PenRepositoryContract.

  • The class takes a JdbcClient in its constructor. It is not a Spring bean yet.
  • A file src/main/resources/schema.sql creates the tables pens and alpacas (with create table if not exists) in SQL that H2 and PostgreSQL both understand.
  • JdbcPenRepositoryTest is a @JdbcTest that extends the contract. Every contract test passes for it. The contract test itself is not changed, except for how it creates its repository (step 3).
  • The ids come from the database (an identity column), not from a counter in your code.

Learning Goals

  • Write plain SQL from Java with JdbcClient (named parameters, update, query)
  • Map objects to rows and rows back to new objects
  • Let the database generate ids and read them back
  • Test an adapter with a slice test and an embedded database
  • Prove two implementations with one contract

Getting Started

  1. Dependencies. Add to your pom.xml: spring-boot-starter-jdbc (compile), org.postgresql:postgresql (scope runtime: the program needs it to talk to PostgreSQL, your code never mentions it), and for tests spring-boot-starter-jdbc-test and com.h2database:h2 (scope test). No versions: the Boot parent manages them. Reload Maven. One warning: from now on the application itself cannot start, because the JDBC starter wants a database connection and you have not told it where the database is. That is the job of Lesson 18. Until then, run tests only. (The web tests do not need a database and stay green. The one @SpringBootTest still passes, because H2 is on its classpath and Boot falls back to it.)
  2. The test class (red). Create JdbcPenRepositoryTest in src/test/java/alpacas: annotate it with @JdbcTest (org.springframework.boot.jdbc.test.autoconfigure.JdbcTest), let it extend PenRepositoryContract, and add a field @Autowired JdbcClient jdbcClient. In createRepository() first empty both tables, jdbcClient.sql("delete from alpacas").update(); and the same for pens (alpacas first: it points at pens), then return new JdbcPenRepository(jdbcClient). Why the deleting? All contract tests save a pen called "Ring" into the same embedded database. @JdbcTest promises to roll every test back, but in this setup the tests you inherit from the contract do not run inside that rolled-back transaction (only tests written in JdbcPenRepositoryTest itself do). Without the two lines, tests that have nothing to do with each other fail with There is already a pen named Ring: "passes alone, fails in the suite". The code does not compile yet: cannot find symbol ... class JdbcPenRepository. Let the IDE create the class with its constructor, make it implement PenRepository, and let every method throw new UnsupportedOperationException() for now.
  3. The trap in your own contract (red). Run JdbcPenRepositoryTest. All nine tests are red with a NullPointerException: Cannot invoke "...JdbcClient.sql(String)" because "this.jdbcClient" is null. Look at the contract: private final PenRepository repository = createRepository();. A field initialiser runs when the test object is constructed. Spring fills @Autowired fields only after construction. At that moment jdbcClient is still null. Fix it in the contract: make the field non-final without initialiser and create the repository in a method annotated @BeforeEach, which JUnit runs after Spring has injected. The in-memory test is unaffected, and you have just learned why a test base class should not create things in field initialisers.
  4. The tables (red). Run again: Table "ALPACAS" not found (H2 reports the name in capitals). Nobody has created the tables. Write src/main/resources/schema.sql:
    • pens: an id (bigint generated by default as identity primary key: the database counts for you) and a name (varchar(100) not null unique).
    • alpacas: an id the same way, pen_id (bigint not null references pens (id), the foreign key you know from the SQL course), name, weight (double precision), fleece_length (integer) and fleece_color (varchar(20): the enum's name as text).
    • Both statements start with create table if not exists. Lesson 18 runs this file against a real database every time the application starts, and it must not fail the second time.
    Run again: the tables exist, and the tests are red for the right reason (UnsupportedOperationException).
  5. Insert a pen (green). Start with savingGivesThePenAndItsAlpacasIds. In save: if the pen has no id, insert into pens (name) values (:name). To learn the id the database chose, give update a GeneratedKeyHolder (org.springframework.jdbc.support) and the name of the key column: .update(keyHolder, "id"); then keyHolder.getKey().longValue() is your id: call pen.assignId(...) with it. Do the same for every alpaca without an id (insert into alpacas (pen_id, ...)). Mind the column names: fleece_color gets alpaca.getFleeceColor().name().
  6. Read pens (green). findByName and findAll. A select with a row mapper turns every row into a new object: .query((row, rowNumber) -> ...), then .list() for many or .optional() for zero or one. Build the Pen from its row, load its alpacas with a second select (where pen_id = :penId), recreate each Alpaca with the constructor, then assignId(row.getLong("id")), and put them into a new Herd. Do not forget order by id (a select without order by promises no order, and findAllReturnsEveryPenInTheOrderItWasSaved needs one). For the case-insensitive name: where lower(name) = lower(:name). Watch the tests turn green one after the other.
  7. Reject a duplicate (green). aSecondNewPenWithTheSameNameIsRejected expects the same IllegalStateException as the in-memory repository. Your unique column would reject it too, but with a database exception of its own, and only for the exact same spelling ("ring" and "Ring" are different texts to it). Check in Java first (findByName) and throw the same exception with the same message. Why does the web layer care? Because PenController maps that exception to 409 and knows nothing else.
  8. Save again (green). The last two tests: savingAgainKeepsOldIdsAndGivesNewAlpacasTheirs and anAlpacaRemovedFromTheHerdIsGoneAfterSaving. For an alpaca that already has an id, run an update ... where id = :id; for one without, an insert. Then delete what is no longer in the herd: delete from alpacas where pen_id = :penId and id not in (:keptIds) with the list of ids you just handled (a List as a parameter fills the brackets). Careful with the empty list: not in () is not valid SQL, so for an empty herd delete all alpacas of the pen.
  9. Run everything. All earlier tests are green, the contract runs twice now (nine tests for each repository), and the application is not touched. Commit.

Hints

Hint 1

The test class and the schema:

@JdbcTest
class JdbcPenRepositoryTest extends PenRepositoryContract {

    @Autowired
    JdbcClient jdbcClient;

    @Override
    PenRepository createRepository() {
        jdbcClient.sql("delete from alpacas").update();
        jdbcClient.sql("delete from pens").update();
        return new JdbcPenRepository(jdbcClient);
    }
}
create table if not exists pens (
    id   bigint generated by default as identity primary key,
    name varchar(100) not null unique
);

create table if not exists alpacas (
    id            bigint generated by default as identity primary key,
    pen_id        bigint not null references pens (id),
    name          varchar(100) not null,
    weight        double precision not null,
    fleece_length integer not null,
    fleece_color  varchar(20) not null
);

In the contract: private PenRepository repository; and @BeforeEach void createTheRepository() { repository = createRepository(); }.

Hint 2

Saving, with generated ids:

private void insertPen(Pen pen) {
    if (findByName(pen.getName()).isPresent()) {
        throw new IllegalStateException("There is already a pen named " + pen.getName());
    }
    KeyHolder keys = new GeneratedKeyHolder();
    jdbc.sql("insert into pens (name) values (:name)")
            .param("name", pen.getName())
            .update(keys, "id");
    pen.assignId(keys.getKey().longValue());
}

private void insertAlpaca(Pen pen, Alpaca alpaca) {
    KeyHolder keys = new GeneratedKeyHolder();
    jdbc.sql("""
                    insert into alpacas (pen_id, name, weight, fleece_length, fleece_color)
                    values (:penId, :name, :weight, :fleeceLength, :fleeceColor)""")
            .param("penId", pen.getId())
            .param("name", alpaca.getName())
            .param("weight", alpaca.getWeight())
            .param("fleeceLength", alpaca.getFleeceLength())
            .param("fleeceColor", alpaca.getFleeceColor().name())
            .update(keys, "id");
    alpaca.assignId(keys.getKey().longValue());
}
Hint 3

The save itself, the update, the delete, and reading:

@Override
public Pen save(Pen pen) {
    if (pen.getId() == null) {
        insertPen(pen);
    }
    List<Long> keptIds = new ArrayList<>();
    for (Alpaca alpaca : pen.getHerd().getAlpacas()) {
        if (alpaca.getId() == null) {
            insertAlpaca(pen, alpaca);
        } else {
            updateAlpaca(alpaca);
        }
        keptIds.add(alpaca.getId());
    }
    deleteAlpacasOfPenExcept(pen, keptIds);
    return pen;
}

private void deleteAlpacasOfPenExcept(Pen pen, List<Long> keptIds) {
    if (keptIds.isEmpty()) {
        jdbc.sql("delete from alpacas where pen_id = :penId")
                .param("penId", pen.getId())
                .update();
    } else {
        jdbc.sql("delete from alpacas where pen_id = :penId and id not in (:keptIds)")
                .param("penId", pen.getId())
                .param("keptIds", keptIds)
                .update();
    }
}

@Override
public Optional<Pen> findByName(String name) {
    return jdbc.sql("select id, name from pens where lower(name) = lower(:name)")
            .param("name", name)
            .query(this::toPen)
            .optional();
}

private Pen toPen(ResultSet row, int rowNumber) throws SQLException {
    long id = row.getLong("id");
    Herd herd = new Herd();
    for (Alpaca alpaca : alpacasOfPen(id)) {
        herd.addAlpaca(alpaca);
    }
    Pen pen = new Pen(row.getString("name"), herd);
    pen.assignId(id);
    return pen;
}

Still to write by yourself, in the same style: updateAlpaca (update alpacas set name = :name, ... where id = :id), findAll (select id, name from pens order by id) and alpacasOfPen (a select with .query((row, n) -> ...) that builds an Alpaca from the constructor with FleeceColor.valueOf(row.getString("fleece_color")) and calls assignId).

When You're Done

Reflect

  • You wrote JdbcPenRepository without starting the application once. What did the contract test give you that clicking through the API would not?
  • findByName builds a fresh Pen from the rows every time. Write down what happens if two requests load the same pen, both add an alpaca, and both save. Which alpaca survives? (Think about the delete ... not in.) Would the in-memory repository behave the same?
  • findAll runs one select for the pens and one more for each pen. With 3 pens that is 4 selects; with 3000, 3001. Do you have to care today? How would you load everything with one select instead?
  • The tests run on H2, the application will run on PostgreSQL. Which of your SQL statements are you sure behave the same on both, and how could you find out for the others?
  • The uniqueness check runs in Java and the column is unique. Why both? Which one catches a race between two requests?
