Lesson 15: Everyone Gets a Number

Story

Ilona is stuck on her list screen. "I show the alpacas of a pen as a list, and I need something that tells one row from another. I use the name, but names are not safe. Delete 'Triple H', add another 'Triple H' tomorrow, and my screen thinks it is the same alpaca. And when Fiona fixes a typo in a name, the address /pens/Cell/alpacas/Triple%20H stops working. Can every alpaca and every pen just get a number?"

Hasi has a second reason. "Soon the farm will live in a database. You know from the SQL course that every row has a primary key. Your objects need that number too. And all the code that loads and stores things must not be mixed into Farm and Herd, or you will rewrite your rules the day you change where the data lives."

This lesson changes only the domain. There is no Spring in it and the app does not start any differently. Lesson 16 plugs the result into your controllers.

🚜 Barn Briefing: a name is not an identity

A name is something an alpaca has; it can be misspelled, changed, or given to the next alpaca. An id is what the alpaca is: a number given once, never changed, never given to anybody else. Two alpacas called Lita are two alpacas with two ids.

Who hands out the number? Not the alpaca itself, and not the person who creates it: when you write new Alpaca("Lita", ...) you cannot know which numbers are taken. The number is given when the alpaca is stored, by whatever does the storing (later: the database). So a new alpaca has no id yet. In Java that is null, which is why the field is a Long (the boxed type, like Double in Lesson 11) and not a long, where "nothing" would look like 0.

🚜 Barn Briefing: a shelf the domain owns

Somewhere your pens must be put away and taken out again. Today that place is the Farm object with its list. In Lesson 17 it will be a database. Your rules (a herd holds 30 alpacas, a name is unique) should not care which.

The usual answer is a repository: an interface that lists what the domain needs from "the shelf" (save this pen, find the pen with this name, give me all pens) and says nothing about how. It lives next to your domain classes, in the package alpacas, because the domain decides what it needs; the implementations come later. Today you write the first one, which keeps pens in a list in memory. Everything that uses the shelf talks to the interface, so swapping the implementation does not touch the user.

One decision is made for you: there is a PenRepository and no AlpacaRepository. An alpaca lives in a pen, so you reach alpacas through their pen, and saving a pen saves its alpacas with it. (The name for "a pen and what belongs to it, stored as one unit" is an aggregate. You do not need the word, but you will meet it. See Martin Fowler on aggregates and on the repository pattern.)

How do you know that a second implementation behaves like the first? You write the tests once, against the interface, in an abstract test class. JUnit does not run an abstract class by itself. A small subclass says only which repository to test, and inherits all the tests. In Lesson 17 the database version gets its own tiny subclass and has to pass the very same tests. This is called a contract test.

Your Task

Add identities and a shelf to the domain, test-first, all in the package alpacas.

  • Alpaca and Pen get Long getId() (null until stored) and void assignId(long id). An id can be assigned once; a second assignId throws IllegalStateException. Existing constructors stay as they are.
  • An interface PenRepository with Pen save(Pen pen), Optional<Pen> findByName(String name) and List<Pen> findAll().
  • A class InMemoryPenRepository implements PenRepository.
  • An abstract PenRepositoryContract test class and the subclass InMemoryPenRepositoryTest.

Learning Goals

  • Explain the difference between a name and an id, and why a new object has no id yet
  • Define an interface from the needs of the caller and keep it in the domain
  • Write one set of tests that every implementation of an interface has to pass
  • Decide what save promises, and test that promise

Getting Started

  1. Identity, red first. Create IdentityTest. Write one test: a new Alpaca has no id (assertNull(alpaca.getId())). It does not compile: cannot find symbol. Let the IDE create getId(), then make it pass. Then, one test and one commit each: assignId(7) makes getId() return 7; a second assignId throws IllegalStateException. Repeat all three for Pen. Why "once"? An id that can change is not an identity, and a bug that gives the same alpaca two numbers is better stopped with an exception than found three weeks later in a database. (The parameter is a plain long on purpose: you cannot assign "nothing".)
  2. Write your test list for the shelf. Do not touch the interface yet. On paper, list what you expect from a repository. Questions to start from: what does save do to a pen that has no id, and to the alpacas inside it? Do two pens get the same id? Is a saved pen found by findByName("rInG")? What does an unknown name give back? In which order does findAll return the pens? What happens when you save the same pen again after adding an alpaca? After removing one? What if a second new pen has a name that is taken (ignoring case)? Then compare with the list in the details below.
  3. The contract class. Create abstract class PenRepositoryContract in src/test/java/alpacas with an abstract method abstract PenRepository createRepository(); and a field private final PenRepository repository = createRepository();. (A field, not a method call inside each test: every test gets one fresh repository, and the test body can use repository directly. If you create a new repository on every call instead, your tests save into one repository and look into another.) Add a helper that builds a pen with one alpaca. Write the first test, "saving gives the pen and its alpacas ids". It does not compile because PenRepository and save do not exist.
  4. The subclass. Create InMemoryPenRepositoryTest extends PenRepositoryContract and implement createRepository() to return new InMemoryPenRepository(). Again red because the class does not exist. Let the IDE create the interface PenRepository (its methods will appear as you need them) and the class, and make the first test pass in the simplest way. Then add the other tests from your list to the contract class, one at a time, each red then green. The subclass never changes again.
  5. Look: what comes back? Before you move on, predict. You save a pen with save, then add an alpaca to its herd without calling save again, then call findByName. Is the new alpaca there? Write a throw-away test and see. Now think about a database: it keeps rows, not your Java objects. Will the new alpaca be there then? Note both answers in docs/api-notes.md. We come back to this in Lesson 17.

Acceptance Criteria

Hints

Hint 1

In Alpaca and Pen the id is a private field private Long id;. assignId checks if (this.id != null) and throws, otherwise sets the field. In the test, write the expected value as 7L (a long) when you compare it with getId().

Hint 2

The whole interface:

public interface PenRepository {

    /** Stores the pen and its alpacas. Whatever has no id yet gets one. Returns the same pen. */
    Pen save(Pen pen);

    Optional<Pen> findByName(String name);

    List<Pen> findAll();
}

Why does save return the pen? So the caller can write Pen saved = repository.save(new Pen(...)) and use the one with the id. A database version will fill the id in the same way.

Hint 3

Shape of save in the in-memory version: a List<Pen> and one counter for ids. If the pen has no id yet, check that its name is free (findByName(...) is already there), give it the next id and add it to the list. Then, for pens new and old, walk through pen.getHerd().getAlpacas() and give every alpaca without an id the next one. Return the pen. For the counter, private final AtomicLong nextId = new AtomicLong(1); and nextId.getAndIncrement() hand out each number safely even if two requests save at the same moment (AtomicLong). findAll returns List.copyOf(pens).

When You're Done

Reflect

  • Why is the interface in the domain package and not next to the SQL code that comes later? Who is allowed to know about whom?
  • Your in-memory repository now checks that a new pen's name is free, and Farm.addPen still does the same check. Two places for one rule. Which one will survive when the farm lives in a database, and what happens to the other?
  • Anybody can call assignId on an alpaca, not only the repository. Is that a problem? How could you make it harder (think about the packages), and what would it cost?
  • The ids 1, 2, 3 restart from 1 each time the app starts. What does that mean for a client that remembered "alpaca 3" yesterday?
  • With no AlpacaRepository, how would you load a single alpaca by its id? Is that a good reason to add one, or a sign that the URL should carry the pen as well?
