Lesson 18: Moving Into the Database

Story

The second repository is ready and proven, but it stands in the workshop: the running application still uses the first one. Ilona is waiting. "Fiona's farm has to survive a restart. Today, please."

Hasi has one condition. "Your company does not run its data on a toy database that lives inside the test. It runs PostgreSQL. So install one the way you will install one at work: in a container, from a file you can commit. Then tell Spring where it is, swap the bean, and restart the app to see whether the farm remembers."

Today the controllers still do not change. The only things that change are one configuration class, one properties file and one new file that describes the database.

Barn Briefing: a database in a container

A container is a small, sealed box with a program in it, started from an image (a ready-made package). You do not install PostgreSQL on your laptop; you ask Podman to start the image postgres:17, and you throw the box away when you are done. A file called compose.yml describes the box: which image, which settings, which port. podman compose up reads that file and starts everything in it. Because the file lives in your repository, a colleague gets the same database with one command.

Three lines in that file deserve a sentence each. environment gives PostgreSQL a database name, a user and a password on its first start. ports: "5432:5432" connects your laptop's port 5432 to the container's, so your application can reach the database at localhost:5432. volumes keeps the data in a storage area outside the box, so the farm survives when the container is stopped and started again (without it, the data would die with the container, which would defeat today's purpose). The password in the file is fine for a throwaway development database on your own machine and never for anything real. Official docs: podman compose.

🌱 Spring Sprout: connection settings and a start-up job

Spring Boot reads src/main/resources/application.properties when it starts. Properties whose names start with spring.datasource. tell it how to connect (url, username, password); from them Boot builds the DataSource, and from the DataSource the JdbcClient you used in Lesson 17. The database driver (the postgresql dependency) is found from the URL, jdbc:postgresql://.... One more property: Boot runs schema.sql automatically only for embedded databases, so for PostgreSQL you must ask for it with spring.sql.init.mode=always. That is why you wrote the script with if not exists.

A bean of type ApplicationRunner is a job that Spring runs once, right after the application has started. Use it for "if the database is empty, stock the farm". Official docs: data access, ApplicationRunner.

Your Task

Run the whole API on PostgreSQL, and keep the web tests independent of any database.

  • A compose.yml in the project root starts PostgreSQL 17 with a database farm (user farm, password farm) on port 5432, with a volume.
  • application.properties connects the application to it and runs schema.sql at start-up.
  • The application's PenRepository bean is a JdbcPenRepository. When the database is empty, the application stores Ring (Lita, Batista) and Cell at start-up; when it is not, it leaves the data alone.
  • The farm survives a restart: pens, alpacas, new alpacas, changed fleece lengths and ids.
  • The web tests (@WebMvcTest) still use the fast in-memory repository, and mvn test works with the database stopped.

Learning Goals

  • Start a development database from a file you commit
  • Configure a Spring Boot application to use it
  • Replace an implementation by changing one configuration class
  • Keep tests independent of the development database
  • Check by hand that data survives a restart

Getting Started

  1. The database. Create compose.yml in the project root (hint 1). Start Podman Desktop if it is not running, then in the project folder: podman compose up -d (-d: in the background). The first run downloads the image, which takes a moment. Check it: podman ps shows a container with postgres:17 and Up. To look inside, podman exec -it <container-name> psql -U farm -d farm opens PostgreSQL's command line (you know the SQL from the SQL course; \q leaves it). The name of the container is in the NAMES column of podman ps. If it does not start on your machine, stop here and tell Thomas: that is a finding for this course.
  2. The connection. Create src/main/resources/application.properties with the four properties from the Sprout (hint 2). Do not start the application yet.
  3. Two repositories (red). Write the new bean first, in a new class DatabaseConfig in package alpacas (annotated @Configuration): a method @Bean PenRepository penRepository(JdbcClient jdbcClient) that returns new JdbcPenRepository(jdbcClient). Spring passes the JdbcClient in as a method parameter, the same way a constructor gets its beans. Run FarmConfigTest (it starts the whole application): BeanDefinitionOverrideException: Invalid bean definition with name 'penRepository'. There are now two @Bean methods called penRepository, the old one in FarmConfig and the new one. (Boot refuses silently replacing one by the other, on purpose. Had you named the new method differently, you would have two beans of the same type, and every constructor that asks for a PenRepository would not know which one you mean.)
  4. The in-memory repository becomes a test fixture. The web tests still want the fast in-memory repository, and the application does not. Move FarmConfig from src/main/java/alpacas/web to src/test/java/alpacas/web (IDE refactoring: Move) and rename it InMemoryFarmConfig. Remove its @Configuration annotation: a test class with that annotation in a scanned package would be found by the application's component scan and bring the second bean back. Without the annotation it is only used where a test asks for it with @Import. Change the four @Import(FarmConfig.class) in the web tests (FarmControllerTest, PenControllerTest, PenChangesTest, ShearingWithRealServiceTest) to InMemoryFarmConfig.class. Run the suite: the web tests are green again. Now only the two tests that start the whole application are interesting: FarmConfigTest and AlpacasApplicationTests.
  5. The silent trap. Those two tests now connect to what application.properties says: the real PostgreSQL. Run them with the container running: they might pass (and FarmConfigTest might even find "Ring" and "Cell" in your development data). A test that passes because your development database happens to be in the right state is a bad test. Stop the container (podman compose stop) and run them again: red, Failed to execute database script ... the connection is refused. Tests must not depend on a service that is up. Put @AutoConfigureTestDatabase (org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase) on both classes: it replaces the real data source by an embedded H2 in this test, and Boot still runs schema.sql on it. Both are green now, with the container stopped.
  6. Stock the farm (test first). FarmConfigTest.farmComesWithTwoPens (Ring, Cell, in that order) is red: nothing creates the pens, since the old FarmConfig that did is gone from the application. Add a second bean to DatabaseConfig: an ApplicationRunner that takes the PenRepository and, if findAll() is empty, saves Ring with Lita and Batista and an empty Cell (hint 3). The test is green. It ran against the embedded database, which starts empty every time, so it proves the stocking; the "only when empty" half you check by hand in the last step.
  7. Run the real thing. Start the container if it is stopped (podman compose up -d), start the application. In the log you should not see an error. Use your docs/requests.http: GET /farm shows 2 pens and 2 alpacas, GET /pens/ring/alpacas/lita has "id":1. Look at the tables with psql: select * from alpacas;.
  8. The test that matters. POST a new alpaca into Cell ("Triple H": the space is %20 in the URL, as in Lesson 14). POST the shear request for Lita. Stop the application and start it again. GET /farm now says 3 alpacas, Lita's fleece is 0, Triple H has his id and is still in Cell, Batista and Lita did not get new ids, and nothing was stocked twice. Fiona's farm remembers. Look at select id, pen_id, name, fleece_length from alpacas order by id; once more. Commit, including compose.yml; but think about the Reflect question about the password first.

Acceptance Criteria

Hints

Hint 1

compose.yml:

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_DB: farm
      POSTGRES_USER: farm
      POSTGRES_PASSWORD: farm
    ports:
      - "5432:5432"
    volumes:
      - farm-data:/var/lib/postgresql/data

volumes:
  farm-data:

Indentation is part of YAML: use spaces, two per level, never tabs. To throw the data away and start fresh: podman compose down -v (-v deletes the volume too).

Hint 2

application.properties:

spring.datasource.url=jdbc:postgresql://localhost:5432/farm
spring.datasource.username=farm
spring.datasource.password=farm
spring.sql.init.mode=always
Hint 3

DatabaseConfig:

@Configuration
class DatabaseConfig {

    @Bean
    PenRepository penRepository(JdbcClient jdbcClient) {
        return new JdbcPenRepository(jdbcClient);
    }

    @Bean
    ApplicationRunner stockTheFarm(PenRepository pens) {
        return args -> {
            if (pens.findAll().isEmpty()) {
                Herd ringHerd = new Herd();
                ringHerd.addAlpaca(new Alpaca("Lita", 70, 4, FleeceColor.WHITE));
                ringHerd.addAlpaca(new Alpaca("Batista", 80, 10, FleeceColor.BROWN));
                pens.save(new Pen("Ring", ringHerd));
                pens.save(new Pen("Cell", new Herd()));
            }
        };
    }
}

The imports are org.springframework.boot.ApplicationRunner and org.springframework.jdbc.core.simple.JdbcClient. The two test classes:

@SpringBootTest
@AutoConfigureTestDatabase
class FarmConfigTest { ... }

When You're Done

Reflect

  • Which files did you change to move from memory to PostgreSQL, and which did you only add? What does that say about the interface you built in Lesson 15?
  • The password farm is in a file in your repository. Why is that acceptable here and not for the company's database? Where would the real password come from? (Hint: Spring can read spring.datasource.password from an environment variable.)
  • The "stock the farm when empty" job lives in the application. What would happen if two copies of the application started at the same moment on an empty database? Is a seed job the right place for data Fiona cares about?
  • Your tests run on H2 and the application on PostgreSQL. Name a bug that H2 could hide from you. What would a team do about that? (One sentence is enough: teams often run the database tests against the real thing in a container, which is a topic for later.)
  • Delete the container with podman compose down (no -v) and start it again. Is the farm still there? Now do it with -v. What is the volume for?
  • Today DatabaseConfig is the only place that says "database". Imagine Fiona wants a second farm on a different server. What would you change?
