Lesson 16: Swapping the Shelf

Story

Ilona is happy about the numbers from Lesson 15, but so far she cannot see them. "My list screen needs the id of every pen and every alpaca in the JSON. Then I stop using names as keys."

Hasi looks at your controllers. "You built a nice shelf last time, and nobody uses it. PenController still asks Spring for a Farm, and a Farm has no ids and cannot be stored in a database. Swap the shelf. And keep an eye on your tests: they are what tells you that you did not break anything."

Today you move the web layer from Farm to PenRepository, and the JSON gets ids. When you finish, the API behaves exactly as before, plus the id fields. That is the point: the existing tests are your safety net, and the red tests along the way are your to-do list.

🌱 Spring Sprout: ask for the interface

A controller says what it needs in its constructor, by type. Spring looks for a bean of that type and passes it in. If the constructor asks for PenRepository, an interface, then any bean that is a PenRepository fits, and the controller never learns which one it got. In your configuration class the @Bean method is declared with the return type PenRepository, so Spring registers the bean under that type: today an InMemoryPenRepository stands behind it, in Lesson 17 a database version. Only the configuration changes, not a single controller. If no bean of the asked type exists, the application cannot start, and the error says exactly that (you will see it twice today). Official docs: dependency injection and @Bean.

Your Task

Replace the Farm bean by a PenRepository bean everywhere in alpacas.web.

  • The JSON of pens (GET /pens, and the response of POST /pens) and of alpacas (every endpoint that returns an alpaca) has a new member id, a number, listed first.
  • All existing behaviour stays: the same status codes, the same error messages, the same Location headers. PUT keeps the alpaca's id.
  • The configuration creates the repository and stores the two start pens in it (Ring with Lita and Batista, and an empty Cell).
  • No class in alpacas.web uses Farm any more.

Learning Goals

  • Program against an interface, and let Spring supply the implementation
  • Change the structure of working code in small steps with the tests as a safety net
  • Use failing tests as a to-do list for a change that touches many classes
  • Know when a changed object has to be stored again

Getting Started

  1. Make the ids visible (red). In PenControllerTest write a test that calls GET /pens, GET /pens/Ring/alpacas and GET /pens/Ring/alpacas/Lita and checks that $[0].id (for the single alpaca: $.id) is not null (.extractingPath("$[0].id").isNotNull()). Do not check for a particular number yet. Add Long id as the first component of AlpacaResponse and of PenSummaryResponse and fix what the compiler complains about (from(...) in AlpacaResponse; give PenSummaryResponse a static from(Pen pen) too, because you build it in two places). The test still fails: the member is there, but its value is null, because the Farm never gave anybody an id. (Jackson writes null as null, as you saw in Lesson 05.) Only the repository hands out ids.
  2. The bean you want (red). Open FarmConfigTest. It injects a Farm. Change it to inject a PenRepository pens and rewrite the two tests: the repository exists, and pens.findAll() contains Ring and Cell in that order (assertThat(pens.findAll()).extracting(pen -> pen.getName()).containsExactly("Ring", "Cell")). Run it. The application context does not start: No qualifying bean of type 'alpacas.PenRepository' available. That is the Sprout from above: nothing is registered under that type.
  3. Register the repository (and watch the avalanche). In FarmConfig replace the method that builds the Farm by a @Bean PenRepository penRepository() that creates an InMemoryPenRepository and calls save for Ring (with its two alpacas) and Cell. Return the repository. Delete the Farm bean. Now the opposite problem: nearly every web test is red, FarmConfigTest included (it starts the whole application): No qualifying bean of type 'alpacas.Farm' available, because your controllers and the shearing service still ask for the Farm. Run the whole suite and look at the list. Now you know the size of the change before you start it. Work through the list class by class; keep running the tests.
  4. FarmController. Change the constructor to ask for PenRepository. The pens are pens.findAll(), the number of alpacas is the sum of Pen::totalAlpacas over them (mapToInt(...).sum()). The farm's name has no home any more, since the Farm object carried it. For now put it in a private static final String FARM_NAME in the controller and think about it in Reflect. FarmControllerTest is green again (FarmConfigTest stays red until the last controller is done).
  5. A repeated line wants a home (test first). In PenController you now need "the pen with this name, or a 404" in five places: pens.findByName(name).orElseThrow(() -> new PenNotFoundException(...)). That is exactly what Farm.findPen did. Before writing it five times, add one more test to PenRepositoryContract: repository.getByName("ring") returns the pen named Ring, and getByName("Nowhere") throws PenNotFoundException. It does not compile. Make it pass with a default method in the interface: a method with a body that every implementation inherits, written once on top of findByName. Keep the exact message from Farm.findPen, The Pen you are looking for Nowhere does not exist: Lesson 08's tests check it. Why in the interface and not in InMemoryPenRepository? The next implementation would have to copy it.
  6. PenController: reading. Ask for PenRepository; replace farm.findPen(x) by pens.getByName(x); GET /pens becomes pens.findAll().stream().map(PenSummaryResponse::from); for ready-to-shear, walk over all pens and collect pen.allAlpacasAreReadyToShear() (flatMap). The compiler will complain about the write endpoints too; leave them for the next step or make them compile in the simplest way. The reading tests of Lessons 05 to 08 should be green.
  7. PenController: writing. A pen or an alpaca that changes must be stored again. For an in-memory list that is invisible (the repository holds the very same objects), but a database holds copies, so make it a rule from today: every change ends with save.
    • POST /pens: Pen pen = pens.save(new Pen(request.name(), new Herd())). The 409 for a duplicate name now comes out of the repository (the same IllegalStateException and the same handler as before); the response uses PenSummaryResponse.from(pen), with the id.
    • POST .../alpacas: add the alpaca to the herd as before, then pens.save(pen). That is the moment the new alpaca gets its id.
    • DELETE: after a successful removeByName, pens.save(pen).
    • PUT: test first. In PenChangesTest, in a pen of your own, create Triple H, read his id from the response, PUT new values and check that the answer has the same id. (Never assert a number like 5: which numbers are taken depends on the tests that ran before in the same shared context, the same sharing you met in Lesson 09. Compare ids with each other.) The test is red: the replacement is a brand new Alpaca without id. Make it green: find the existing alpaca first (findByName(...), 404 if it is missing, as in Lesson 12), build the replacement, give it the old id with assignId, swap it in with herd.replace(...) and pens.save(pen).
  8. ShearingService. ShearingServiceTest builds a Farm and passes it to the service. Change the test first: create an InMemoryPenRepository, save the Ring pen into it, pass that to new ShearingService(...). Red (the constructor takes a Farm). Change the service: ask for the repository, pens.getByName(penName), and call pens.save(pen) after the shepherd has sheared. In ShearingWithRealServiceTest the injected Farm becomes an injected PenRepository, and farm.addPen(...) becomes pens.save(...). Notice that the service test needed no mock: the in-memory repository is a real, fast implementation, and that is one more reason to have one.
  9. Last checks. Search the project for Farm: nothing in alpacas.web uses it. The class itself and its FarmTest are still in alpacas and still green; decide in Reflect what to do with them. Run all tests. Then start the app and look at the ids with your docs/requests.http: GET /pens starts with {"id":1,"name":"Ring",..., GET /pens/Ring/alpacas shows Lita as 2 and Batista as 3, Cell is 4 (the pens and alpacas share one counter, so the numbers are not "1, 2, 3 per kind"). Post a new pen and see what it gets. Restart the app and look again.

Acceptance Criteria

Hints

Hint 1

The configuration:

@Bean
PenRepository penRepository() {
    Herd ringHerd = new Herd();
    ringHerd.addAlpaca(new Alpaca("Lita", 70, 4, FleeceColor.WHITE));
    ringHerd.addAlpaca(new Alpaca("Batista", 80, 10, FleeceColor.BROWN));

    PenRepository pens = new InMemoryPenRepository();
    pens.save(new Pen("Ring", ringHerd));
    pens.save(new Pen("Cell", new Herd()));
    return pens;
}

The declared return type is the interface. If you declare InMemoryPenRepository instead, the controllers still work, but you have written the implementation's name into your configuration for no reason.

Hint 2

The default method, the response mapping and the ready-to-shear list:

default Pen getByName(String name) {
    return findByName(name).orElseThrow(
            () -> new PenNotFoundException("The Pen you are looking for " + name + " does not exist"));
}
static PenSummaryResponse from(Pen pen) {
    return new PenSummaryResponse(pen.getId(), pen.getName(), pen.totalAlpacas());
}
pens.findAll().stream()
        .flatMap(pen -> pen.allAlpacasAreReadyToShear().stream())
        .map(AlpacaResponse::from)
        .toList();
Hint 3

The PUT:

Pen pen = pens.getByName(penName);
Alpaca existing = pen.getHerd().findByName(alpacaName)
        .orElseThrow(() -> new AlpacaNotFoundException(alpacaName, penName));
Alpaca replacement = request.toAlpaca(alpacaName);
replacement.assignId(existing.getId());
pen.getHerd().replace(replacement);
pens.save(pen);
return AlpacaResponse.from(replacement);

For the test: read the id out of the POST response body with a JSON path library (JsonPath.read(body, "$.id") from com.jayway.jsonpath, already on your test classpath), or by GETting the alpaca before the PUT. The text of the response is mvc.get().uri(...).exchange().getResponse().getContentAsString(), and the method that calls it declares throws Exception.

When You're Done

Reflect

  • You made a change that touched every controller. How did the red tests help you, and what would you have done without them?
  • The farm's name is a constant in FarmController now. Where should it live, so that Fiona could rename her farm without a new build? (Hint: Spring reads application.properties.)
  • The class Farm is not used by the application any more, but its 24 tests are green. Do you delete it and its tests, keep it, or give it a new job? What does a class cost that nobody uses?
  • Both PenController and ShearingService ask the repository for a pen, change it, and save it. What if two requests do that to the same pen at the same moment? (The in-memory version shares the very same objects between requests. A database makes this question harder, not easier.)
  • Look at the URLs. Names are still the addresses; the ids only appear in the JSON. When would you add /alpacas/{id}? What would Ilona have to change?
